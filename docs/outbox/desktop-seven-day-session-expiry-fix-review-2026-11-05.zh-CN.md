**本稿审查时的决定：暂不进入实现开发。** 采纳审核对证据链、客户需求来源和原方案范围的纠正；原方案 A 不再作为“最小修复”推荐。方案 B 的修改范围更小，可作为优先候选，但必须先明确其续期语义，并由产品／客户确认对书面需求 R04 的变更。

复核发现方案 B 的两项论据也需要修正：后台定时刷新会产生真正的 `session_ready`，因此“每次校验成功顺延 7 天”不等于“用户空闲 7 天”；现有手机号静默重建会话路径意味着 Gateway 的 180 天只限制单个会话，不保证用户每 180 天重新认证。两点已用现有实现的隔离本地测试复现，不能作为已经成立的安全保证写入方案。

本次仅完成只读调查、隔离行为验证和文档修订，未修改客户端实现、生产配置或数据，未提交或发布。

## 一 客户需求与需要确认的变更

已读取客户原始 Word `循证_PC端新增登录功能.docx`，原文为：

> 登录态通过 Token 维持，默认有效期为 7 天，过期后需重新登录。

客户端实施评审 `medevidence-desktop-sms-key-login-implementation-review-2026-09-08.zh-CN.md` 将其登记为 R04；第 7.2 节进一步明确从成功登录起算，冷启动和自动刷新不滚动延长，并说明这是产品本地会话规则，不是对所有 API 客户端的服务端安全控制。

因此，方案 A 的独立模型会话延续，以及方案 B 的滑动续期，都改变了已书面确认的行为。**必须取得产品／客户对 R04 新解释的明确确认，内部技术审核不能替代这项决定。** 确认记录应写明续期依据、后台行为、临时登录是否包含，以及是否另设最长重新认证周期；“行业常规”不能替代客户需求变更记录。

原始短信接口资料写明初始 access token 有效期 10 天、refresh token 有效期 30 天；实际 access 到期时间仍以每次合法响应的 `expires_in` 为准。第 7 天达到的是客户端产品期限，不能据此称外部 token 已经过期。

## 四 方案 B 必须区分的两种语义

### B1 按服务端成功校验滚动七天

这对应审核者提出的直接实现：只有底层 `phone-auth.ts` 发布真正成功的 `session_ready`，且无错误、账户一致、运行来源正确时，才将短信本地 `expiresAt` 更新为校验成功时间加 7 天并持久化。不能在外层已把 legacy fallback 映射成 `session_ready` 之后判断。

其实际产品含义是：**应用持续运行且后台授权校验成功就持续续期；连续 7 天没有成功校验，则本地登录到期。** 用户可能一直没有键鼠操作、窗口处于后台或最小化，但刷新定时器仍工作。该方案可以避免此次活跃任务在最初第 7 天被登出，并保持正常情况下模型和支付共享本地期限；它不保证“用户 7 天不用就退出”。

`phone-auth.ts:scheduleRefresh()` 在 access token 到期前 60 秒执行刷新、授权校验并发布 `session_ready`。原事件中也可见约 14 分钟的刷新周期。单纯把续期放进订阅回调，不能区分后台续期、用户操作或活跃任务。

### B2 按用户或任务活动计算空闲七天

若产品真正要求“7 天不用则退出”，必须定义哪些行为构成使用，并取得相应信号，例如用户主动交互或有任务正在执行；定时刷新、网络恢复和普通后台事件不能单独算作活动。

期限应锚定符合定义的活动时间，在服务端校验成功后才确认续期。不能仅判断“最近发生过活动”后，每次后台校验都用当前时间再加 7 天，否则仍会无活动续期。正在运行的长任务、暂停任务、纯等待以及休眠恢复的归属也须明确。这将增加活动信号和测试范围，不是仅修改几行订阅回调。

### 两项已完成的本地行为验证

使用现有 `createDesktopAuth` 实现和原测试的本地 fixture，测试文件置于独立临时目录；只有本机 loopback 服务和虚构凭证，未更改产品源码或生产账户。结果为 **2 项通过、24 次断言**。

1. 登录后不进行任何用户操作，缩短 fixture 的 Gateway access 周期以触发定时器。观察到 1 次后台 refresh 和新的无错误 `session_ready`。这证明 B1 会把后台刷新作为续期依据。
2. 保留未过期的短信本地记录，把 fixture 的 Gateway 会话设为绝对到期后重新初始化。观察到 1 次 `login/start`、0 次新短信登录，最终恢复 `session_ready`。这证明 `initialize()` 丢弃到期会话后，外层 `retryGateway()` 可以用保存的 mobile 创建新会话。

第二项验证的是现有恢复路径，不表示已经实现方案 B。B1 持续延长短信期限后，会使“短信本地期限仍有效、Gateway 会话已到期”这一条件在长时间使用中可达。因此不能承诺每 180 天要求用户重新认证。若需要跨 Gateway 会话的最大登录寿命，必须另行保存并执行不随静默重建改变的认证边界，或阻止到期后的静默重建；两者都要计入范围，不能声称 `phone-auth.ts` 及恢复语义完全不受影响。

### 候选方案选择

| 方案 | 可承诺的行为 | 需要接受的代价 |
| --- | --- | --- |
| B1 校验后滚动七天 | 持续成功校验则续期，无成功校验 7 天到期 | 后台运行也会续期；不承诺跨会话 180 天强制重新认证 |
| B2 活动空闲七天 | 按明确的用户／任务活动定义到期 | 需要活动信号和持久化规则，实施范围大于订阅回调 |
| A 独立延续模型会话 | 短信本地期限不再决定模型登录 | 增加状态和恢复策略，支付与模型登录分裂，需要独立威胁模型 |

**建议优先评审 B1，但以产品／客户接受上述准确含义为前提。** 若必须满足真正的活动空闲或跨会话最长认证期限，则选择并细化 B2／认证边界，不以 B1 的少量代码代替需求。

本轮候选默认只改变短信登录模式；临时登录保留原固定 7 天规则。扩大到临时登录须在确认记录中显式说明。

## 五 B1 的最小实现边界

以下为 R04 变更获准后的实现要求，不是开发批准。主要改动应集中在客户端 `packages/desktop/src/main/desktop-auth.ts`、相关测试及必要提示文本，不引入 A 的到期后受限恢复策略。

1. **续期来源。** 在底层成功状态映射之前判断 `next.status === "session_ready"` 且无错误，同时核对短信绑定账户、Gateway Subject 和已安装运行授权。legacy ready、legacy fallback、account ready、错误及仅 HTTP 200 都不能作为续期依据。
2. **期限与代际。** 仅允许原本尚未到期的短信会话续期；到期后才返回的旧响应不能使其复活。沿用 generation 校验，退出、切号、取消后的回包不能写回旧账户。
3. **原子保存。** 在现有串行写队列内读取最新短信记录并只合并期限，避免用旧快照覆盖并发支付刷新后的 access／refresh token 或 `refreshPending`。成功落盘后再更新内存和安排下一次定时器。`subscribe()` 不是可等待的异步事务，不能简单添加一个未处理异常的 async 回调。
4. **写入失败。** 保存失败时不宣称已续期，不把内存期限无限延长；保留原有效期限并展示可恢复的存储错误。不得因为一个续期写入失败立即注销仍在原期限内的会话。
5. **保留现有检查。** `schedule()`、`initialize()`、`retainRuntime()` 等继续使用本地期限，不大规模改写状态机；新期限距成功校验最多 7 天。实际实现需验证原到期定时器与在途保存的竞争，不保证“完全不动这些函数”就能通过验收。
6. **服务端边界。** 不改变单个 Gateway 会话的期限、刷新轮换、账户／Key／权益校验和退出行为。保留历史 fallback 兼容，但不能把 fallback 当成新的续期证据。跨会话最长认证期限按上一节的产品决定处理。
7. **支付共同修复。** `openPayment()` 遇到本地 `session_expired` 时返回重新登录提示，不调用全局 `fail()`／`logoutDevice()`，不发送本地期限已过的外部 token。真正的外部 token 过期仍按现有合法刷新／拒绝逻辑处理，不能伪造其期限。

支付这一处修正只能消除“点击支付触发全局登出”的额外路径，**单独做它不能消除原有第 7 天定时器退出**。它也不允许到期后继续使用外部 token。支付错误后不得自动调用现有 `openLogin`，因为该操作就是退出；显式重新登录的界面应说明对当前任务的影响。

不通过修改常量为 30／180 天宣称完成修复，不修改服务器配置或数据库。B1 预计可沿用现有存储字段；若新增活动信息或跨会话绝对边界，应重新评估存储兼容和范围。

## 六 修订后的验收条件

原 A 的受限恢复用例不再作为 B1 的新增行为要求；保留现有回归，并加入滑动续期的触发、保存和竞争验证。

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| T01 | 短信登录后持续成功校验，模型任务跨过最初第 7 天 | 续期持久化，任务不中断，无由原期限引起的 logout／runtime clear |
| T02 | 真正的底层成功状态、错误状态、legacy ready／fallback 分别到达 | 只有符合条件的底层成功状态续期 |
| T03 | 续期后重启；连续 7 天未成功校验后重启 | 前者按已保存期限恢复，后者按到期处理，不能先恢复再把过期期限延长 |
| T04 | Gateway 绝对到期而短信滚动期限仍有效 | 记录现有静默重建行为；若产品要求最长重新认证边界，必须验证禁止越界重建，不能误报已有 180 天保证 |
| T05 | 机器存在手工 legacy Key，触发原有 fallback | 保持原兼容范围；fallback 本身不能延长短信期限 |
| T06 | 账户不一致、退出、切号及迟到的成功回包 | 不续期、不恢复上个账户，保持原账户隔离 |
| T07 | 本地期限已过时点击支付，外部 access token 可能仍有效 | 不发送该 token、不打开支付页；支付处理不主动全局登出，返回准确提示 |
| T08 | 外部 access token 真正到期或 refresh 失败 | 使用真实 `accessExpiresAt` 和服务端响应处理，不把它与本地期限混为一谈 |
| T09 | 并发支付 token 刷新与模型成功校验续期 | 不覆盖新 token、refreshPending 或 Subject；重启读取一致 |
| T10 | 续期保存失败、到期定时器与保存竞争 | 原期限仍有效时不立即登出；不虚报续期，到期和退出后的写入不能复活登录 |
| T11 | 503、429、超时、账户禁用、Key 撤销和权益失效 | 错误不续期；保留原重试、撤销及能力限制语义 |
| T12 | 临时登录运行、重启、重试跨过固定第 7 天 | 保持原规则，不被短信续期分支影响 |
| T13 | 最小化／无人操作但后台刷新成功；存在长任务；休眠超过期限 | B1 明确允许后台续期；若选 B2，按已批准活动定义判断；休眠到期后不能由迟到响应复活 |
| T14 | 存储升级、主动退出后重启、Mac 与 Windows 安装包 | 兼容既有数据，退出持续生效，目标平台真实长任务验证通过 |
