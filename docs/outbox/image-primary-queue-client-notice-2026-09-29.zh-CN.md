# 生图固定首选模型与延长排队：客户端配合通知

日期：2026-09-29。**状态：后端代码及测试已完成，正在准备发布；上线时间以发布回执为准。** 本文可先用于客户端开发与联调，不表示线上容量已经扩大。

我们将生图策略调整为优先保证模型一致性：使用本地 Qwen-Image-2.1，关闭自动跨模型回退。繁忙时在现有队列等待，容量或期限耗尽则明确失败，不再自动调用 GPT Image、Grok、Gemini 等其他生图模型。公网模型名称和同步接口保持不变：`medcode-image-default`、`POST /gateway/images/generations`。

## 后端行为

- 全服务共 12 个在途名额，按两个执行名额加十个等待名额设计；不是每个用户各十个。实际最多同时执行两个任务。CT 优先级、内存与温度准入仍可能使实际执行并发降为一或暂停，因此不能承诺固定出图时间或始终有两张卡可用。
- 排队最长 600 秒，单次实际推理仍限 180 秒；图片池从收到请求起的总期限为 780 秒。排队不会在派发时重置总期限。
- Gateway 等待 Qwen 的期限为 790 秒，整个生图请求预算为 810 秒。超出容量返回 429；资源不可用或排队到期通常返回 503；Gateway/上游超时可能返回 504。请按返回的错误码、HTTP 状态及 Retry-After 处理，不依赖英文报错文本。
- 接口仍一次请求返回最终图片，没有新增异步 job ID、进度流或查询接口。现有 `/gateway/model-calls/:id` 模型回执协议不覆盖生图 POST，不能用它证明图片请求没有执行，也不能假定图片 POST 已有幂等去重。
- 断开后尚未派发的任务会退出等待；已经派发的任务可能仍在 GPU 上完成或清理，后端保持占用保护，确认结束前不会把同一 GPU 交给下一次执行。取消不等于瞬间停止推理。

## 请客户端团队修改

1. **生图 HTTP 总等待改为至少 900,000 毫秒（15 分钟）。** 当前源码默认 `210_000`，配置入口是 `MEDCODE_IMAGE_CLIENT_TIMEOUT_MS`。可以先通过启动环境配置验证，但正式版本应调整默认值，并确认环境变量确实传到运行 image 工具的进程。外层工具、步骤、任务或无进展看门狗也不能在生图仍合法等待时先行中断；用户主动取消仍要生效。配置变更无法由 Gateway 自动替客户端完成。
2. **限制本机在途生图数量，建议最多两个。** 模型一次返回多条 image 工具调用时，客户端将其放入本地队列，按名额逐个发送；跨会话共用此生图并发限制。不要通过提高模型/工具并发来追求出图速度。若整批有很多张，后续本地排队项从实际发出 HTTP 时开始计算其请求期限；本地队列应支持用户取消。
3. **等待状态保持可见，但不编造进度。** 可以显示“正在排队或生成，繁忙时可能需要数分钟”，并保留取消操作。当前协议不能区分排队与推理，也不提供队列位置。请移除写死的“等待超过 3 分钟”文案，使报错与实际配置一致。
4. **避免不确定结果后的自动重发。** 网络中断、客户端超时、503/504 不证明原任务从未执行；不要由网络层、工具层、Agent 同时重试，更不要为同一张图并行补发。保留已成功的图片，仅让用户明确重试缺失项。429 按 Retry-After 提示稍后重试；如实现自动重试，必须先核对该错误是否明确发生在未派发阶段，并限制次数及整项总期限。
5. **记录定位信息，控制诊断量。** 保留工具调用 ID、Gateway request ID、发送/结束时间、等待耗时、取消原因、状态码和最终图片路径；等待阶段只做低频状态更新，不高频重复上传诊断或重复调用生图。

这些修改不改变提示词、尺寸、格式和最终图片解析方式。固定模型能避免自动切换带来的质量差异，但 Qwen 本身仍可能生成错字；图片含有文字时仍需预览核对，不能把 HTTP 200 当成文字内容正确。

## 联调验收

- 模型一次返回 7 条 image 工具调用：客户端最多两个请求在途，其余本地等待，最终结果正确对应各个调用，不重复生成。
- 服务端受控提交 12 个请求：最多两个实际执行；容量未释放时第 13 个请求被拒绝，且没有其他生图模型调用。容量是全服务共享，测试时须排除其他流量并使用受控后端。
- 模拟超过 210 秒、但小于后端总期限的正常等待：客户端继续等待，外层任务不先行报错。
- 取消排队、取消执行、断网、429、503、504：无隐式重发，无重复图片；已成功图片保留，状态和错误可定位。
- 服务端模拟测试验证并发与取消；真实图片单独验收内容和中文字形。不要用故障注入或高并发真实生图直接压生产。
