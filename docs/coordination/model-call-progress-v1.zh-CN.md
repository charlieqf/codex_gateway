# Gateway 模型调用运行状态扩展契约 v1

日期：2026-10-13。面向 Gateway 与 Desktop 联调。

状态：Gateway `94b60ae` 已于北京时间 2026-10-13 08:28:52 部署。progress 与 goldencode 单次请求 900 秒预算均已通过公网自测；实际观察到 waiting_upstream、reasoning 和模型活动时间。验证范围及限制见[发布记录](../operations/gateway-progress-release-2026-10-13.zh-CN.md)。

本契约在[模型调用回执与恢复 v1](model-call-recovery-v1.zh-CN.md)上可选增加 `progress`，用于说明服务端模型调用阶段。既有鉴权、回执状态、结果恢复、查询限流和防重复执行规则保持有效。

## 接口与兼容规则

接口仍为 `GET /gateway/model-calls/:id`。顶层 `version: 1` 及 `X-MedCode-Model-Call-Contract-Version: 1` 不变；此版本号本身不表示支持 progress。

- `progress` 是可选对象。本期仅在 `state: "running"` 且当前执行进程持有有效运行快照时返回。
- 本期 `completed`、`failed`、`unknown`、`expired` 均省略 progress。终态由顶层 `state` 与原 `response` 判断，不新增完成或失败 phase。
- Gateway 返回 progress 时应完整提供下列六个字段；明确可空字段使用 `null`。尚未初始化运行快照时省略整个对象。
- Desktop 必须兼容整个对象缺失、字段缺失以及未来新增字段；字段不合法或出现未知 phase 时降级为一般等待状态，不影响原回执恢复。
- 顶层 state 始终优先。进入终态或 unknown/expired 后，客户端清除先前的运行阶段；不得把旧 progress 当作任务仍在执行的证据。
- progress 只属于原模型调用，不包含本地工具执行、文档读取、文件交付完成或整个用户任务的进度。也不表示排队位置、完成百分比或剩余生成时间。

## 字段定义

所有时间戳均为服务端 UTC 时间，使用 RFC 3339 字符串，固定毫秒精度和 `Z` 后缀，例如 `2026-10-13T02:00:00.000Z`；不使用北京时间字符串或 Unix 秒数。

| 字段 | JSON 类型与单位 | 含义 |
| --- | --- | --- |
| `phase` | string | 下表定义的服务端模型处理阶段。表示最近可确认的阶段，不保证此刻仍有模型输出。 |
| `started_at` | UTC string | 原请求启用模型调用总预算的时刻，与该请求 deadline 的计时起点一致；不是 call ID 中的时间、查询时间或整个用户任务开始时间。内部重试与修复不重置。 |
| `deadline_at` | UTC string 或 null | 原请求实际生效的总截止时间，已考虑服务端策略及客户端更短的请求预算。没有有限截止时间时为 null；不得把配置的 900 秒当作所有请求都实际获批 900 秒。 |
| `last_model_activity_at` | UTC string 或 null | Gateway 最近一次观察到有效模型输出增量的时间；整个原请求尚未观察到有效增量时为 null。它是 Gateway 观察时间，不是上游自报时间。 |
| `elapsed_ms` | 非负整数，毫秒 | 从 started_at 对应计时起点至本次查询快照的累计耗时，用单调计时计算；包括等待、模型输出、校验、重试及修复，不因查询或重试归零。超时收尾期间可略大于总预算。 |
| `attempt_index` | 非负整数，无单位 | 当前或最近一次实际发起的上游模型尝试序号。尚未发起为 0，首次为 1；内部重试、换上游、格式修复引发新模型调用时各加 1。查询回执、心跳、本地校验不增加。不是允许重试次数，也不是客户端工具步骤数。 |

`started_at` 和有限的 `deadline_at` 在同一原请求中固定。`attempt_index`、`elapsed_ms` 在服务端连续快照中不倒退。Desktop 对同一调用至多保持一个查询在途，并忽略停止或终态之后到达的旧查询响应。

## 阶段枚举

| phase | 服务端事实 | 建议界面文案 |
| --- | --- | --- |
| `waiting_upstream` | 准备调用或已发起当前尝试，尚未收到该尝试的有效模型输出增量 | 等待模型响应 |
| `reasoning` | 最近收到的是可识别的非空推理增量 | 已收到推理内容，等待结果 |
| `generating` | 最近收到正文或工具调用参数等有效输出增量 | 正在接收模型结果 |
| `validating` | Gateway 正在校验已收集的模型结果或工具参数 | 正在校验模型结果 |
| `retrying` | 已决定进行内部重试或格式修复，正在准备下一次模型调用 | 正在重试或修复模型结果 |

枚举是阶段，不是只进不退的进度条。下一次尝试发起时增加 attempt_index，并回到 waiting_upstream；同一尝试可以在 reasoning 与 generating 之间切换。格式修复调用发起后按其实际活动切换阶段，不一直停留在 retrying。同一个上游事件同时含推理和正文/工具增量时，generating 优先。

`last_model_activity_at` 仅由成功解析到的非空推理、正文、工具调用名称或参数等有效模型输出增量更新。下列活动均不得更新它：

- Gateway SSE 心跳或上游心跳、注释、空帧；
- HTTP 响应头、原始网络字节、单独的 role、usage、finish_reason 或 DONE；
- 回执查询、elapsed_ms 刷新、本地校验、重试开始或客户端工具执行。

重试期间保留原请求最近一次模型活动时间，不伪造为重试开始时间；从未收到有效增量则仍为 null。phase 转换不必伴随模型活动时间变化。长时间没有增量可以提示“最近一段时间未收到模型新输出”，但不能仅据此断言模型停止或任务失败。

服务端在模型事件到达时更新当前回执的内存字段，查询时读取快照并计算 elapsed_ms；不增加定时刷新、进度历史或数据库写入。进度观察失败不能影响模型执行，不返回原始推理文本、工具参数或供应商凭据。

## 查询响应示例

以下为联调示例，表示原调用开始 125 秒、首次尝试收到推理内容，实际总预算为 900 秒。

```json
{
  "version": 1,
  "id": "<original_call_id>",
  "state": "running",
  "request_id": "<original_request_id>",
  "progress": {
    "phase": "reasoning",
    "started_at": "2026-10-13T02:00:00.000Z",
    "deadline_at": "2026-10-13T02:15:00.000Z",
    "last_model_activity_at": "2026-10-13T02:02:04.000Z",
    "elapsed_ms": 125000,
    "attempt_index": 1
  }
}
```

等待首次上游调用时，attempt_index 为 0；发出首次调用但还没有有效模型输出时，attempt_index 为 1，last_model_activity_at 仍为 null。这两种情况都可以使用 waiting_upstream。

## 查询退避与结果恢复

`Retry-After` 继续只表达查询退避，不表达模型剩余耗时。Gateway 当前限流响应使用整数秒；Desktop 继续兼容 HTTP-date。应读取本次 GET 响应的头，不能将 `response.headers` 中原模型请求的 Retry-After 当成本次查询退避。

建议等待首个有效结果时约每 30 秒查询一次，加入少量抖动并控制账号级并发；收到有效 Retry-After 后，下次查询不得早于指定时刻。休眠或网络恢复可触发及时查询，但不能越过退避期限。查询错误或字段缺失不得自动触发新的模型 POST。

running 时保留原请求；查询不保证模型可以脱离原连接在后台继续执行。确认获得可恢复的终态后，客户端按原协议接回响应，避免与已消费的流内容或已经执行的工具重复。主动停止后结束轮询和后续工具执行。

## 单次调用预算适配（2026-10-29 修订）

本次 Gateway 修改将请求头 `x-medcode-request-timeout-ms` 的允许范围放宽为整数 1 至 1800000 毫秒；实际预算仍取服务端策略与客户端所请求上限的较小值。此修订尚未发布，现网仍拒绝大于 900000 的值。先发布并验证 Gateway，再让客户端将现有上限改为 1800000；不新增能力字段或协商步骤。客户端增大请求头不能突破尚未调整的服务端预算。

1800 秒针对单次原请求，内部多次模型尝试共享该预算。Desktop 还需取用户任务剩余时间及显式请求预算的较小值，不能因为查询、重试或休眠恢复而给原调用重新分配预算。默认 120 秒连接/流无数据保护与总预算分开处理，保持原值。

存在 progress 且 deadline_at 非 null 时，可用 `max(0, deadline_at - started_at - elapsed_ms)` 估算快照时的剩余预算，再考虑本地经过时间及网络延迟。不要直接用 deadline_at 减客户端墙钟，以免设备时钟偏差导致误判。该估算仅用于预算与界面，不替代服务端终态；预算到零也不证明原调用未执行或结果不可恢复。

progress 缺失时继续使用已保存的请求预算与恢复协议。进入恢复路径后的 30 秒滚动查询窗口、原调用预算之后的 60 秒结果恢复宽限保留，仍受任务剩余时间约束；不能在每次恢复时重新计时。查询收尾不延长服务端生成时间。原连接仍有心跳时的并行收据查询不保证查询失败 30 秒后退出。

请求超时头参与原调用指纹。同一个 call ID 的重复 POST 必须保留最初的请求头；不能把已发出的 900000 改成 1800000 后用同一 ID 重发。恢复优先 GET；之后的独立逻辑调用才使用调整后的预算和 ID。

## 联调验收

1. 旧回执不含 progress，或含未知 phase/字段时，Desktop 仍能等待、恢复和消费终态。
2. 仅持续心跳、role、usage 或 DONE 不更新 last_model_activity_at；真实推理、正文与工具增量按定义更新，时间戳格式及毫秒单位正确。
3. 重试/修复令 attempt_index 递增，started_at 和 deadline_at 不变；查询不改变模型活动时间、尝试次数或原执行预算。
4. 650 至 850 秒完成的请求可正常消费；900 秒耗尽、客户端选择更短预算及任务预算更短时均正确收尾。
5. 服务端已完成但原流交付丢失时，可从原回执恢复；休眠恢复、退避、主动停止、查询乱序和原流与查询同时完成均不造成重复工具执行。
6. 进程退出、回执不可恢复或跨主体/scope 查询不能返回陈旧 running/progress。终态只按现有回执协议判断，不用阶段推断成功。

发布验收应记录两个模型的实际 1800 秒配置、三个 adapter 超时和容器停止宽限。客户端上限必须在权威 R760 Gateway 发布验证之后调整，不能以本契约文档已修改代替服务端已上线。

## 本地实现与部署配置

progress 复用现有回执的活动对象和鉴权路径，只保存在内存；结果完成、失败或连接取消时清理。没有新增数据库表、定时器、外部状态接口或 SSE 事件，既有回执结果格式与重放规则不变。

`config/gateway.example.env` 与 `config/gateway.container.example.env` 给出以下配置：

```dotenv
MEDCODE_CHAT_REQUEST_TIMEOUTS_JSON={"models":{"goldencode":1800000,"goldencode-d":1800000}}
MEDCODE_TENCENT_TOKENHUB_TIMEOUT_MS=1800000
MEDCODE_TIANKUAN_TIMEOUT_MS=1800000
MEDCODE_TOKENSWITCH_TIMEOUT_MS=1800000
```

部署时将两个目标模型的 1800000 合并到现有 timeout JSON，保留其他 models、runtimes、defaultMs 及 `MEDCODE_CHAT_REQUEST_TIMEOUT_MS`，同步核对三个目标 adapter。示例文件不是生产配置，不能整份覆盖生产环境；其他模型的请求期限策略不随本次调整。应用停机等待为 1860 秒，容器停止宽限须为 1870 秒。上游自身的更短硬限制仍可能提前结束调用，需线上联调验证。当前实现与发布前检查见[长推理时限记录](../implementation/long-reasoning-timeout-2026-10-29.zh-CN.md)。

历史进度功能验证（不代表本次 30 分钟调整已上线）：自审精简后类型检查通过，9 个相关测试文件共 490 项通过。覆盖 Gateway 主请求路径、回执恢复、状态隔离、真实连接取消、上游解析、工具修复与重试，以及共享截止时间。删去重复的观察容错用例，将当时的 900 秒边界并入既有期限测试；修复测试核对两次尝试的开始时间和截止时间保持不变。历史边界使用虚拟时钟验证，没有以真实付费模型运行 15 分钟的测试替代线上验收。
