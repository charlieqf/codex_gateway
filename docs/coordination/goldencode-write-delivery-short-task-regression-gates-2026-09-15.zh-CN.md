# write-delivery：短任务回归风险与首期发布门槛（2026-09-15）

状态：R3 开发契约的回归门槛。请求声明修订及离线 SDK 对照已通过，业务实现、完整短任务对照和生产灰度尚未完成。本文不是“已证明零回归”的声明。

## 判断

**有回归风险，不能仅凭 S 只针对超长输出，就声称短任务完全不受影响。** S 的实际转换入口可以很窄，但共享的工具注册、请求预处理、SDK 响应适配、重试和文件事务代码会影响其他请求。

“短、小”应按请求的实际行为判断：正常短问答和合规 write 不进入 S；即使用户只输入一句话，只要生成结果超过客户端声明上限，也可能应进入 S。是否转换不以 prompt 长短或统一的 4,000 字符为门槛，而以实际原 schema 校验失败为依据。

R2 的 20 项检查存在三个已复现的缺口，R3 已修复并通过 60 项契约检查。另有 7 次实际 SDK 本地 HTTP 对照通过，证明该条件下的 body 字节一致和普通文本不等待 EOF；完整业务路径、旧 HTTP 中间件、延迟和文件行为仍须验收。

## 本次发现及首期范围调整

| 风险 | 具体影响 | 首期约束 |
| --- | --- | --- |
| 通用修复一律要求剩余至少 120 秒 | 原期限 30/60 秒的短工具请求，即使缺字段可在数秒修好，也永远不再获得原有纠错机会 | 撤回其作为 A 首期通用条件的提案；普通非长度错误保留当前次数、参数和原 deadline 行为。120 秒只作为后续新增模型恢复路径的候选，不直接套用旧路径 |
| 全部 write 改成 4,000 字符片段 | 原本一次完成的 5,000 字符文件变成多次调用，额外引入 done、暂存、格式化和权限状态 | 首期不启用 B，不替换普通 write，不降低其 12,000/32,000 声明上限；4,000 仅是 S 传输分片候选 |
| 所有能力响应都完整缓冲 | 正常流式问答可能等整个响应结束才显示，取消和错误传递也会变慢 | 只有具有有效 S manifest 的实际交付响应才完整检查；仅有 accepted capability 不足以触发缓冲。普通 Response.body 保持既有流式路径 |
| 新封装 schema 改变普通模型输入 | 即使未发生超长输出，也可能改变选工具、prompt token、额度估计或 tool_choice 推断 | 传输保留工具不进入模型 prompt/tools，不计入模型工具个数和推断，不改变原工具顺序；只统计实际发给模型的对应工具开销 |
| 新客户端连接旧 Gateway | R2 示例把封装放进普通 tools，可能传给旧模型 | R3 已改为本地注册 + activeTools 排除 + schema SHA header，SDK/body parser 对照通过；实际 HTTP 中间件、混合实例与回滚待验收 |
| 通用 write 共用新事务入口或表迁移 | 正常小文件可能开始等待整轮完成、重复询权、丢 result_files，甚至影响原事务恢复 | 新事务只服务 S，普通 write 保留原提交/权限/结果路径；迁移可向前添加，不重写旧行与唯一约束，检查启动和回滚兼容 |
| 过宽的禁止重试或严格接收检查 | 将缺字段、网络错误、并行无冲突工具也拒绝，降低原有成功率 | 禁止条件按明确错误/协议上下文匹配；S 的“唯一工具、整响应检查”不能用于全部普通响应 |
| 多个 S 同时缓冲或做哈希/文件处理 | 长任务的内存、同步 CPU 或全局锁可能拖慢同机其他短任务 | 加有界内存/交付并发，按文件而非全局串行；进行混合负载测试，不能只验证单个大文件 |

首期 A 的行为变化仅限：明确受支持 write 的内容 maxLength 超限，增加可诊断信息并停止已确认无效的 Gateway 全量重生成。S 对满足协商、完整性和语义条件的这类输出尝试无损交付。其他 schema 修复的优化单独提交和评估。

## 新客户端与旧 Gateway：已确定的声明与剩余验收

当前 Gateway 的 `parseChatCompletionRequest` 会解析 body.tools，`collectNativeClientTools` 把 request.tools 传给 provider；普通工具估计也使用该数组。R2 仅要求新 Gateway 过滤 write_delivery_v1，不能保护不会识别新协议的旧 Gateway。

按 Desktop R2 回执确定：SDK 边界本地注册接收器，activeTools 只列原普通工具，HTTP body.tools 保持原集合。新增 X-MedCode-Write-Delivery-Schema-SHA256，摘要固定 schema 文件原始 UTF-8 字节；Gateway 用版本和摘要查有限协议注册表，未知摘要不接受 S，普通请求照常。字段与 R3 样例已作为开发契约固定。实际旧 HTTP 中间件对新增头的处理仍须实测，不把本地 body parser 通过扩大为部署验证。

仅在首轮得到“支持”后才把新工具放进后续普通 tools 也不充分：滚动发布、回滚或负载分配可能让下一请求落到旧版本。若选择发现/缓存方案，必须给出覆盖这些情况的保证和测试。

使用 [R3 success.example.json](../../artifacts/write-delivery-contract-r3-2026-09-15/success.example.json)，其中 sdk_registered_tools 与 request_body.tools 已分离；R2 仅保留历史，不再作为实现请求格式。实际 SDK 6.0.168 的 7 次合成 HTTP 对照确认 body 字节一致、普通流在 EOF 前到达、本地接收器可执行且不出现在网络 tools。无额外能力探测请求。

## 必须保持的普通请求行为

1. 未实际触发 S 时，模型接收的 messages、普通 tools/schema/顺序、tool_choice、reasoning_effort、max_tokens 和模型路由，与基线相同；用合成请求捕获对比，不能只看最终回答“差不多”。
2. 普通响应不新增等待 EOF 才转发的步骤；保持原流式边界、错误与取消传递。S 已协商但未发生转换也属于普通路径。
3. 合规 write 不改工具名、mode/chunk、权限语义、写入时机、格式化/BOM 处理和 result_files；不新建 S 暂存事务。
4. 普通工具多调用按既有行为执行，不把 S 的唯一封装限制扩展给 read/search/export_document 或不同文件的合法调用。
5. 正常短任务不增加模型调用、后台自动重试或额外的每任务能力探测 HTTP 请求；若采用启动期能力发现，其开销和失败回退另行说明。
6. 不因无关能力头的缺失而拒绝正常工作。无有效 S 清单的保留工具调用仍须禁止执行，这个保护在接收器执行前完成，不要求预先缓冲所有普通流。
7. 错误与超时的优化不能将“短请求设置了较小 deadline”自动视为不可修复。保留原来的原期限和调用次数预算，除非独立修复已给出明确收益与验收。

## 回归对照矩阵

基线采用变更前已验证提交，候选采用含 A/S 的实际构建；固定合成上游事件，分别测试 S 关闭、已声明但未转换、确实转换。以下为完整业务验收矩阵；离线 fixture/SDK 已覆盖其中部分格式与流式条件，不能代替实际构建验收。

| 场景 | 验收要点 |
| --- | --- |
| 无工具的一句话问答，stream=true/false | 模型请求不变、调用 1 次，普通流式首内容不等待 EOF；状态与取消行为不变 |
| 有 write 工具但模型返回短文本 | 不因增加接收能力改变 auto/required 推断，无 S 缓冲或事务 |
| 1/100/3,999/4,000/4,001/5,000 字符合规小文件 | 原 schema 允许时均保持一次普通 write；4,001 不是自动分片阈值 |
| content 在 12,000/32,000 上限前、等于上限、刚超过上限 | 前两者保持旧路径；只有准确超限且满足其他条件才转换，字符口径按各声明检查 |
| 中文/emoji/转义/BOM 小文件 | 原行为与边界不因 UTF-16/code point/UTF-8 混用而改变 |
| 小文件 overwrite、append、无 done、非最终 chunk | 权限次数、文件字节、提交时机与结果标识同基线；不强制新增 done |
| write 后紧接 read/run | 后续工具看到已提交内容，无整轮结束等待 |
| read/search/export_document、合法多工具 | 不进入 S，不套用唯一调用限制或新增文件锁 |
| 小工具缺 required 字段，期限 30/60 秒 | 在预算足够、上游能修正的固定用例中保留原有纠错成功；不被通用 120 秒门槛阻断 |
| 原有 429/网络错误/用户取消 | 重试归属、次数和截止时间与基线一致，S 标记不误伤其他错误 |
| 新客户端 + 旧 Gateway / 新 Gateway + 旧客户端 / 回滚期间混合实例 | 普通模型 tools 不出现传输保留函数；旧端不收到不支持的封装；普通短任务可完成 |
| 新能力已接受但无 manifest | 走既有流式路径，不能仅因 accepted 头而缓存全响应 |
| malformed manifest 或伪造封装 | 无文件副作用；明确协议错误；不把异常结果回退为未经检查的工具执行 |
| 同会话前一步发生过 S，后一步是短任务 | 历史映射不造成 tool-call/result 不配对、上下文暴涨或再次写入 |
| 多个 S 与短请求同时运行 | 普通请求延迟、内存及事件循环滞后无明显恶化；不引入全局文件锁 |
| 新版本首次启动、禁用 S 和回滚旧构建 | 原 DB、普通写入与旧 artifact 流程正常；未提交 S 状态不能被旧流程误消费 |

性能需记录普通流式首内容、总耗时、每请求模型调用数与用量、进程内存/事件循环滞后。绝对通过阈值应在固定本地延迟基线测出后确定，并报告样本量；不能用几次真实模型调用的随机快慢证明没有回归。

## 发布与当前验证状态

首期保持 B/C 关闭，普通错误重试策略保持基线；新接收器只对显式受控的新能力启用。先完成上面的交叉版本和混合负载验收，再对少量账号灰度。对照中出现任何语义差异、额外模型调用、普通流等待 EOF 或文件结果变化，应停止扩大范围。

开关关闭只能阻止新的 S 转换；已被客户端接受的 S 交付仍须按 journal 完成或明确终止，不能改走普通 append 重放。遇到业务回归应能关闭 S，保留 A 的明确长度错误诊断，同时不恢复无效的整篇生成。

当前完成 R3 契约 60 项检查和 SDK 7 次本地 HTTP 对照，结果见[验证摘要](../../artifacts/write-delivery-contract-r3-2026-09-15/validation-summary.json)。请求格式的架构阻塞已解决，不重复请求设计确认；实际业务构建和完整矩阵尚未验收，因此**尚不能承诺短任务无回归**。
