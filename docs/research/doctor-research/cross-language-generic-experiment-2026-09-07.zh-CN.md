# Doctor Search 通用跨语言检索实验（2026-09-07）

结论：已完成 64 个真实组合测试，其中 32 个由独立 Agent 选例并核对。独立集认对人物 25 / 32，姓名、机构、科室事实均正确 24 / 32，同时满足预先规定的引文与任职证据要求仅 1 / 32。未发现独立案例答案或配对译名泄漏，但发现音译消歧、科室关系和证据核验缺陷，以及一项保留的专科排序偏置。当前仍是隔离实验原型，未替换生产 Doctor Search，不能作为全球检索已经修复的验收结论。

## 目的与边界

验证姓名、医院或机构、科室三个字段各自使用中文或英文时，能否通过通用检索代码找到具有公开证据的同一位医生。测试覆盖每人的全部 `2 × 2 × 2 = 8` 种组合。

这是检索及身份核验实验，不是完整报告生成、论文归属、PDF 导出或公网客户端端到端验收。生产环境仍使用之前的实现；本实验没有发布新版本，也没有创建用户、开通套餐或修改平台路由。

## 数据与独立性

- 开发集：Felix Mottaghy、Markus Schwaiger、Paola Anna Erba、赵玉沛，共 32 个组合。前三人用于重现原问题，赵玉沛用于中国医生回归。
- 独立保留集：由另一位 Agent 自行选取 4 人，覆盖中国、澳大利亚、加拿大、丹麦，共 32 个组合。实现者在冻结代码前不知道这些人的身份或输入。
- 外国医生的中文姓名若没有查到官方译名，明确标记为测试音译。它检验音译歧义处理能力，不能当作医院认可的标准姓名。
- 独立 Agent 将输入矩阵和核对答案分开保存。调用模型时只传当前用例的姓名、机构、科室；不传另一语言的配对值、预期姓名、核对来源或标准答案。
- 每次模型调用独立，不携带其他组合的聊天历史。网页抓取在同一批实验内共享缓存，因此耗时不能直接等同于每个请求冷启动时的生产耗时。

实现代码在运行独立案例前冻结；保留集运行后不针对这些医生增加别名、修订提示词或调参。完整文件哈希记录在 `artifacts/doctor-cross-language-2026-09-07/frozen-manifest.json`，不是仅对提示词计算的摘要。

## 通用代码怎么工作

1. 调用现有 Research 内部 Gateway 的腾讯 `glm-5.3`，为三个输入字段生成至多两组英文或当地语言检索假设。机构和科室分别处理，姓名可能是原生中文名，也可能是外国姓名的中文音译。模型生成的写法只是待验证假设。
2. 使用 SerpAPI Google 搜索。组合姓名与机构、姓名与科室，并保留仅姓名的检索；不固定中国的地区或语言参数。候选结果合并去重，最多 40 条。
3. 第二次调用 GLM 从真实搜索结果中选择至多 6 个网页，并可选择搜索结果里已经出现的机构域名做一次站内补搜。代码不接收模型凭空给出的 URL、候选 ID 或未观察到的域名。抓取总量最多 12 个网页。
4. 通过已有安全 HTTP 抓取器获取正文，保留原始 URL、正文摘要哈希及来源内容。搜索摘要只用于导航，不能作为确认身份的证据。
5. 第三次调用 GLM，独立阅读原输入和抓取正文，判断姓名、机构、科室是否对应，区分现任、曾任和时间不明。它不会接收规划阶段的结论作为答案。
6. 代码核验来源编号和逐字引文是否存在，拒绝未知来源、编造引文、不匹配的拉丁姓名，以及模型仍不确定的音译。证据不足返回未找到或歧义，不自动填入模型记忆中的履历。

实验核心只依赖 Node 内置加密模块，没有导入生产机构别名表、医生特例或固定医院域名。独立运行器复用现有模型客户端与抓取器，不调用生产 Doctor Search 的身份映射逻辑。

正常完整路径为 3 次 LLM 调用、至多 5 次搜索、至多 12 次网页抓取。实验设置单例 240 秒、单次模型调用 65 秒、并发 2；这些是实验限制，尚未接入生产 WorkflowContext 的持久化预算、计费和取消流程。

## 反向检验

每位医生的全英文用例成功走到验证阶段后，再用同一批抓取正文进行两个独立验证调用：

- 把机构改为不存在的 `Unrelated Example Hospital 9XYZ`。
- 把科室改为 `Ophthalmology`，由独立核对判断该医生是否确实没有对应眼科关联。

这些检查只验证身份核验阶段会不会强行认领错误的机构或科室；不代表完整负例搜索链路已覆盖。前面阶段失败而没有执行的负对照必须记为未执行。

本地 7 项测试覆盖引文约束、未知来源、姓名不匹配、音译不确定、检索计划约束、网页摘录、候选来源选择和矩阵完整性，已通过。盲测完成后仅扩展了测试文件中的数据完整性检查，使开发集与独立集都检查三个字段的中英文值及每人八个唯一组合；这一项定向复跑通过，未修改被测算法、运行器或盲测输入。

## 已发现的问题及后续实现要求

开发集已经发现以下问题，保留集使用同一冻结版本，以便真实暴露泛化限制：

- 中文音译不是一一对应翻译。例如同一个中文姓氏可能被还原成多个英文拼写。检索假设若全部选错，后续核验无法弥补没有抓到正确资料的问题。
- 模型偶尔输出无效 JSON。当前实验直接记录失败，不通过手工补答案或无限重试掩盖。
- 模型偶尔给出未在搜索结果中出现的机构域名。当前校验会终止整个案例，即使其已选择的其他网页有效；这属于实现过于严格，生产接入时应将可选补搜的无效输出与已有证据处理分开。
- 当前来源类别限制比较粗；官方网站中的项目参与者页、旧任职资料和专业学会简历需要准确辨别，而不能只靠通用网页排序。
- 逐字引文存在不等于语义关系成立。独立案例评价已逐项检查机构层级、人物和科室关系、当前或历史任职，并发现了实际错误。
- 独立静态审计发现追加搜索结果的标题打分含 `nuklearmedizin` 专科词。它不参与翻译，也不是医生特例，但属于潜在开发集排序偏置，因此本版不能被描述为完全没有样本相关启发式。
- 所有引文统一要求至少 4 个字符，会误拒绝真实存在的两字或三字中文姓名；当前错误名也没有准确区分“引文太短”和“正文不存在引文”。
- 网页缓存保留失败 Promise，首次抓取的瞬时失败会影响后续组合；正文摘录也可能遗漏原页面后半段的科室或任职日期。
- 当前机制围绕中文、英文输入测试；不能据此宣称日文、阿拉伯文、所有姓名变体及所有机构都已通过。

后续生产方案需要加入有界的结构化输出处理、基于已检索证据的姓名歧义消解、现有运行预算与来源审计集成，并以新的独立案例检验修改效果。任职判断还需要显式传入核验日期，区分网页发布日期、资料中的任职期间及抓取日期。不能再次通过固定医生或医院别名让这批样本通过。

对于无法可靠还原的音译，下一步应检索原始机构及科室的官方团队/人员页，从网页中的真实姓名候选反向核对音译，而不是不断让模型猜姓氏。对于医院、研究机构和临床科室的关系，须保留输入中的组织层级，并将“研究方向相关”与“该科室任职”明确分开。必要的多来源联合佐证也应留下关联证据，不能由模型在正文没有支持时自行补齐。

结构化结果还需明确约束：未确认或否定的状态不能保留可被下游当作已确认身份的 `matches`。如果需要展示歧义候选，应使用独立的候选字段及不确定性标签，并与最终匹配分开。
