# 人物研究输入扩展：服务端实现研究

日期：2026-10-12

调查时基线：本地 `main`，提交 `4897a56`；调查开始时相关服务端源码无未提交修改，后续本地实现及验证记录见第 10、11 节。

范围：前 9 节保留初始代码调查与实现建议；第 10、11 节记录随后完成的本地实现、自审与真实模型验证；第 12 节记录发布结果。服务端 `088f11a` 已于 2026-10-12 发布到 R760。

## 1. 结论与最小范围

可以在现有身份调查、背景生成、事实复核和产物生成流程内实现。无需新增 agent、研究服务、公共接口版本或人物任职数据库。

本期只处理三项业务变化：

1. 所属机构可为医院、企业、学会、大学或研究所，沿用 `hospital` 字段。
2. `department` 可缺省；有值时只表示实际科室、部门、团队等组织单元。`title` 沿用职务／职称含义。
3. 增加 `interview_topics`、`interview_focus`，用于学术问答的内容选择，不作为人物身份事实。

本期不做人物类型路由、多任职管理、通用身份补录、新报告类型、独立身份缓存服务或新的重试调度系统。

## 3. 请求解析与内部数据

### 3.1 沿用现有数据结构

`ResearchDoctorInput.department` 已经是 `string | null`。HTTP 层放宽为缺省或 `null` 后，归一化为 `null`，不写“无科室”等占位内容。

在 `DoctorResearchRunInput` 上追加两个可选属性：

```ts
interviewTopics?: string[];
interviewFocus?: string;
```

HTTP 层仍使用 `snake_case`，内部沿用 `camelCase`。缺省或显式 `null` 的新字段在规范化对象中省略，不补空数组、空字符串或额外 `null` 属性。理由是当前请求哈希直接取规范化对象的 JSON；改变旧对象形状会破坏原有幂等重试。

校验按对接文档实现：主题 1–3 项，每项 1–100 字符，去首尾空白后不重复；重点最多 1000 字符。沿用已有文本的 Unicode／控制字符校验。主题顺序保留，因为表示优先级。

### 3.2 修复重复字段校验

顶层按请求写法校验一次。仅在存在 `doctor` 对象时，对该对象执行身份字段白名单校验；平铺写法不再把整个正文当成纯身份对象二次校验。

拒绝未知字段、拒绝身份字段在顶层与对象内混填的规则保留。新增采访字段只允许在顶层。旧 `title` 等字段原有空白归一化行为保持不变，避免顺带收紧旧合同。

### 3.3 三种指纹不要混用

| 指纹 | 应包含什么 | 兼容要求 |
| --- | --- | --- |
| 创建请求哈希 | 完整规范化请求，含新增主题和重点 | 原有合法请求哈希逐字节保持不变；同一幂等键改主题仍报冲突 |
| 人物准入指纹、身份调查输入哈希 | 保持现有人物信息范围；不加入主题和重点 | 非空科室的旧哈希保持不变；缺省科室用稳定的 `null` 表示；不借机改成仅姓名＋机构 |
| 背景生成状态指纹 | 原有人物、身份、语言、来源，再加实际提供的主题和重点 | 无新增字段时保留旧算法结果；改变主题或重点不能恢复另一份生成状态 |

这里只保证主题变化不改变身份指纹，不承诺跨任务复用身份调查。现有数据是任务内持久化状态，不是全局身份缓存。

## 4. 身份调查：取消不存在的科室要求，保留证据要求

推荐最小内部调整：`InvestigatedIdentity.department` 允许 `null`，不再用职务或研究主题代填。具体任职仍通过现有、带来源的 `profile.positions`／`claims` 表达，无需新增角色对象。

核验规则：

- 必须有能够把这个人和该机构关联起来的证据，并经过独立身份复核；姓名同名、机构共现、目录相邻文字都不够。
- 人物、机构、来源可信度三类引文仍必需。没有已核实科室时，最少 3 条分类引文；有已核实科室时再要求科室引文，至少 4 条。它们是证据分类，不是 3 或 4 个不同网页；同一官方介绍可以支持多个事实。
- 引文必须来自已捕获文本，保留原文匹配、来源存在性、搜索摘要需已读页面佐证等检查。减少一个不适用的证据类别，不等于降低人物关联判断标准。
- 输入科室缺省时，不主动要求医院科室或执业证明；输入科室存在但未核实时，允许在人物已能唯一确认的情况下记录限制，不能将该科室标记为已验证。
- 输入与证据矛盾时区分“没查到”与“有冲突”。人员、机构或影响身份判断的科室冲突未解决时，返回现有 `identity_not_resolved` 路径。
- 任职原文、历史任职和当前任职继续按时间理解；不能因输入了“理事”“教授”就认定当前有效。

调查者与独立复核者的提示词必须一起改，避免一方允许无科室、另一方仍要求补齐。两者都不接收采访主题作为身份匹配条件。

### 减少无效循环

先保持既有模型、搜索和总时长预算，优先消除错误的科室证明要求。调查提示明确为独立复核预留调用次数，最后一个可用调用不能用于启动无法完成复核的新调查。

对“相同结论、相同证据再次提交且已被拒绝”的情况，可增加小型重复检测：在持久化 observations 中记录结论和证据的签名，无新增证据时直接反馈上次问题，避免再次付费复核；允许调查者读取新资料、修正结论或明确结束。不要按反馈文字相似就提前判定身份失败，也不要用不断提高预算代替修正核验条件。

该优化与字段扩展分别验证；即使先不加入重复检测，也应先让正确的无科室身份能够通过。

## 5. 主题传递、生成与结果

数据流为：

`HTTP 正文 → 规范化输入 → research_runs.input_json → worker → preparePracticalProfile → author 与 editor → assemblePracticalProfile → 结果与文件`。

`preparePracticalProfile` 增加可选主题和重点。生成者与复核者都收到相同需求，内容规则为：

1. 有主题时，围绕主题生成总共 5 组学术问答；重点只控制侧重和受众。
2. 无主题时，继续从已核实专业背景确定方向；资料不足不得编造。
3. 专题文献可以支持一般学术参考回答，不能据此声称是受访者的研究成果或本人观点。
4. 主题和重点属于不可信输入数据，不能更改工具权限、证据要求和问答数量。与本期学术范围冲突的要求不能被照单执行。
5. 不新增通用 `needs_input` 补字段状态；资料不足或范围不符仍通过现有失败／限制机制处理，不保证所有输入都成功。

结果组装需同步处理：

- 统一计算匹配项，供 workflow 和最终组装复用。只有请求提供了科室、结论确实核实该组织单元、且有科室引文时才可标记 `department`；语言翻译是否对应由独立复核判断，不靠字符串相等。
- 无科室时返回 `["institution"]`；不能用采访主题凑 `research_topic` 匹配项。姓名关联是身份核验前提，不需要为凑数量增加新的匹配枚举。
- `contracts.ts` 将匹配项最小数量改为 1，影响模型输出和最终结果两个 schema。公共结果字段不变，但旧客户端的严格 schema 校验可能不兼容，须联调。
- 身份说明只拼接有依据的非空值，不能输出文字 `null` 或空科室。
- 关键词优先使用明确提供的采访主题；否则使用已核实的科室或有来源的研究方向。仍无具体领域时可使用中性的“专业背景”／`Professional background` 作为文档关键词，不能凭空补医学专业。中性关键词不能代替学术问答的证据要求。
- `source_coverage.limitations` 保留未核实细节；输入回显仍与核验事实分开。

## 6. 存储、版本及恢复

现有 `input_json` 存储 JSON 对象，可容纳两个可选字段；科室可空也已被核心类型和结果字段支持。本次看不到必须增加 SQL 列或业务表的理由。

需要防止三类兼容破坏：

1. **旧请求哈希变化**：不要为旧请求补两个空字段；固定旧样本的规范化 JSON、完整请求哈希和身份指纹作为回归基线。
2. **旧任务被版本门禁拒绝**：`skill-definition.ts`、store 创建任务时写死的版本和 `runUsesCurrentFirstPartySkill` 必须一致。可选输入扩展不需要新增公共版本，也不必单独新增内部输入版本。若实现时升级 prompt／skill 元数据，应显式允许本次新旧两套已知组合，不能放行任意版本。
3. **恢复时重置研究预算**：旧状态里的已完成搜索、页面、模型调用计数不能因格式变化而清零。新字段缺省时保持旧生成指纹；新任务存储主题后必须参与指纹。新增的可选状态信息可缺省，旧状态的已验证结论按旧格式读取，不能无条件套用新的科室语义。

建议以兼容读取现有状态、仅新增任务采用新规则为目标。实现时先用旧身份已完成、旧生成待复核和新任务中途重启三个夹具验证恢复，再决定是否需要单独的内部状态版本及转换函数。若需要转换，只转换本次已知格式，保留证据和计数；不要建设通用迁移框架。

历史成功结果和文件不回写。新旧任务混跑时要核对结果渲染所依赖的内容策略标记，避免仅升级标记就落入旧学术报告模板。

## 9. 尚需在实现中验证的两点

- 旧持久化状态能否以可选字段扩展兼容读取，还是必须增加一个受限的状态版本转换：需要重启恢复夹具验证，不能仅凭类型检查判断。
- 调用方是否使用旧结果 JSON Schema 的“至少两项匹配”限制：对接方需核查；已在对接文档明确这个变化。

这两点不妨碍先完成本地实现和自动验证；生产启用前必须闭环。

## 10. 本地实现记录

已完成：

- 两个可选采访字段的解析、归一化、入库、生成及复核传递；修复平铺请求的重复白名单校验。
- 身份 agent 支持科室为 `null`，按适用情况要求三类或四类引文，继续执行原文检查和独立复核。身份调查不接收采访主题。
- 统一匹配依据组装；无科室只返回机构匹配；仅有科室或主题的单项匹配仍不能通过结果 schema。
- 空科室身份说明、文档关键词和机构展示标签适配。输入科室未核实时由服务端补充限制说明。
- 不新增数据库表、不变更公共接口路径、不升级内部版本门禁，旧格式仍可读取；旧请求缺省新增字段时不改变哈希。
- 新主题和重点参与生成状态指纹，不参与人物准入指纹。以旧格式候选草稿状态验证恢复，保留付费调用计数。
- 无科室人物的完整任务经过数据库入库、模型桩调查／复核、四类文件生成及结果提交；模拟租约过期后由另一个 worker 接替，未重复已完成的搜索、页面读取和初稿生成。
