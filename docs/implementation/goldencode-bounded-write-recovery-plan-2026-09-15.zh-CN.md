# goldencode 超长参数与有序分块写入修复方案（2026-09-15）

状态：**A/S 首期开发契约按 R3 冻结；Gateway 实现及本地集成测试已完成，正在准备受控部署和公网冒烟。** Desktop 文件事务与完整联合验收仍待完成，S 仅进入专用测试账号灰度，B/C 保持关闭。以下方案正文保留设计阶段背景，当前发布状态以随后形成的部署回执为准。

本轮材料：[Desktop 第二轮回执](../../../medevidence-opencode-stable/docs/outbox/goldencode-bounded-write-client-review-r2-2026-09-15.zh-CN.md)；[Gateway R3 回执](../outbox/goldencode-bounded-write-gateway-review-response-r3-2026-09-15.zh-CN.md)；[R3 开发契约及完整附件](../coordination/goldencode-write-delivery-v1-contract-draft-2026-09-15.zh-CN.md)。S 的字段与检查边界以 R3 为准；本次冻结开发接口，不替代上线或性能验收。

短任务回归补充：[风险与发布门槛](../coordination/goldencode-write-delivery-short-task-regression-gates-2026-09-15.zh-CN.md)。首期收窄为 A 的明确长度错误与 S 的完整结果交付；不全局更换 write、不启用 B/C、不把 120 秒门槛用于原有普通 schema 修复。声明已改为 SDK 本地注册 + activeTools 排除接收器 + 固定 schema SHA 请求头；旧 HTTP 中间件及滚动/回滚仍需验收。

核心目标：**优先保留并交付已经生成的完整结果；返回校验失败只是无法安全恢复时的兜底。** 完整内容仅因长度超限而被拒绝时，优先采用 S 的无损交付；首次生成分块和受限模型纠错用于预防或补救其他情况。

依据：[超时调查](../operations/tool-validation-timeout-investigation-2026-09-15.zh-CN.md)。已确认的直接触发是 write.content 超过客户端声明的 maxLength，随后 Gateway 重新生成并耗尽原请求的 600 秒期限。下面区分 A/S 开发契约与 B/C 后续提案，均不是已发布能力。

### 事实、提案与验证边界

- 已验证：线上出现完整工具输出后 maxLength 校验失败及总期限内重新生成；本地 4 项隔离用例复现现有行为，5 项历史相关回归通过。
- 已核对源码：首次输出仍可在 Gateway 的校验处理阶段访问；Desktop 已有部分短片封装和文件事务基础，但云端端到端路径未接通。
- 尚未验证：S 的同响应批次交付、客户端聚合与提交、零额外模型调用下的文件完成效果，以及本文提出的新恢复契约。此前测试通过不等于这些新能力已经实现或验收。
- R3 已检查：60 项契约检查通过，修复原始 arguments 超限、实际 X-Request-Id 绑定及重复 choice 的三个缺口。实际 SDK 的 7 次合成本地 HTTP 对照通过；未覆盖生产适配器、TLS、旧 HTTP 中间件、文件/崩溃、native 或性能。
- 整份内容传输完整不代表内容在语义上满足用户任务；最终文件仍沿用适用的工具校验与任务验收。不能只凭哈希一致或模型 done=true 宣告任务正确完成。

## 目标与交付拆分

| 交付 | 具体结果 | 适用范围 |
| --- | --- | --- |
| A：Gateway 错误分类与重试止损 | 明确的文件内容长度超限不再触发 Gateway 内部整次重新生成；其他 schema 修复维持原有次数、参数和总期限行为 | 包括旧客户端 |
| S：保留完整结果并无损交付 | 已生成完整、只因内容长度失败的写入，在同一响应中拆成可验证的传输片段；不增加模型调用 | Gateway 与支持事务分片的新客户端 |
| B：Desktop 管理有序片段 | 模型每次只交付一个短片段；客户端拥有序号、去重、暂存和完成判断 | 新客户端能力灰度 |
| C：恢复契约与端到端验收 | 只有一个恢复方；发生长度超限时最多一次短片纠错，期限与次数不重置 | Gateway 与新客户端联合启用 |

A 可以独立实施，先减少已知无效的第二次长调用，但不是完整解决方案。优先交付 A + S + B 所需的事务接收最小实现，让已生成结果能够落盘；随后完善 B 的首次生成分块与 C 的受限模型纠错。只完成 A 时，应明确对外说明“更早返回具体错误”，不能声称长文件自动恢复已经上线。

第一版覆盖 goldencode 的普通文本文件写入，如 Markdown、TXT、HTML 和源码。export_document 的结构化幻灯片缺字段仍走通用校验修复。二进制文件、未知第三方工具、edit/apply_patch 不自动套用文本拆分。

## S：完整结果的无损交付，优先于再次调用模型

### 为什么可行

当前 `runNativeClientTools` 在调用 `nativeCollectionToResult` 校验时，`first.toolCalls` 仍保留刚收集到的完整参数。失败后现有代码只取错误摘要进入重试，没有把原生成内容带入下一次请求。处理当下可以使用这份完整结果，无需由模型重新写一遍。

已确认的 beta.34 案例中，上游已返回 HTTP 200、finish_reason=tool_calls，日志明确是 content 的 maxLength 失败，属于应优先评估此路径的场景。判断入口必须检查实际参数和其他约束；不能仅凭日志的一条 maxLength 文本就宣称已满足所有前提。历史参数正文未保存在本次取证资料中，这个方案不能凭摘要恢复过去已丢失的正文。

### 准入条件

第一版仅接管一个完整的普通文件写入：响应结束状态正常、JSON 可完整解析、工具是客户端明确声明的受支持写入工具，并且除内容字段 maxLength 外的参数约束全部有效。原目标路径、overwrite/append 语义、原写入是否属于更大文件的中间片等必须可明确保留。

新客户端必须支持版本契约，在 SDK 本地注册接收器，HTTP 仅通过固定 schema SHA 等头部声明，body.tools 不增加接收器。完整 payload 仍受总字节与片数限制。未知 schema、混合副作用工具、损坏 Unicode、截断或其他字段错误不强行套用。普通云端 write 不包含内部 done，缺少 done 不是错误；S 保留原 mode/chunk，排除 artifact 等其他模式。

### 具体处理

1. 在 `nativeCollectionToResult` 的错误分支、进入 `nativeValidationRetryPlan` 之前尝试 `tryLosslessWriteDelivery`。它接收仍在内存中的原始完整参数；失败则明确说明不符合哪条准入条件。
2. 按实际接收 schema 的字符和序列化字节预算切片，不丢字符、不补字符、不改路径和原操作。Gateway 对原完整内容计算一次 payload 字节长度和 SHA-256，并产生稳定 delivery_id；切分计算不得依赖模型。
3. 同一响应仅交付一个 write_delivery_v1 调用，包含全部传输片段。接收器不进入 HTTP 普通 tools 或模型工具注册表；以每次实际 HTTP nonce、最终可信 origin/主体、实际响应头和原始参数摘要绑定来源。客户端在 MedcodeStream.stream 之前完整检查唯一 choice/工具、正常结束和全部摘要，原始 arguments 在累积及 parse 前受有效字节上限约束。processor 排序和 execute 自查不能替代此步骤。具体报文以 R3 为准。
4. 客户端验证拼接后的原始 payload 与 Gateway 给出的总长度和哈希完全一致，再按原 overwrite/append 语义处理目标文件。追加时 payload 哈希仅代表新追加内容，不等于原文件加新内容的最终哈希；最终文件哈希由客户端基于实际原文件计算。
5. 换行规范化、BOM 与格式化在完整拼装后按既有工具规则执行，避免逐片处理改变边界内容。权限、目标文件冲突及完整文件校验仍然执行。
6. 传输分片全部收到只表示原始一次 write 已完整交付。S 按原工具语义在工具成功前提交这一次普通写入，供后续 read/run 使用；若原 write 是更大文件的中间片，不能因此新增整个文件完成标识。无 chunk 的普通 write 可产生既有文件结果，不能等待一个原 schema 并不存在的 done。
7. 保留原 provider call 的用量；模型调用次数为 1。记录 `lossless_delivery_attempted/delivered`，客户端另报 staged/committed/failed；Gateway 完成交付不能直接等同于用户文件已成功落盘。

S 不受“剩余至少 120 秒才能启动模型纠错”的门槛限制，因为它不再调用模型；仍遵守原始网络期限、取消和传输上限。首轮已经用去 505 秒时，只要完整结果满足准入条件且剩余时间足够交付，仍应尝试无损传输，而不是仅因剩余不足 120 秒直接丢弃结果。传输耗时需联调测量，不能预先保证几秒完成。

第一版使用同一请求内存与响应交付，不新增公网文件链接或持久化全文库。若未来要支持 Gateway 响应丢失后重新下载，应另行设计绑定主体、短有效期和访问校验的结果保留机制；此次不能承诺已经具备该能力。

### 三条处理路径

| 已取得的结果 | 优先动作 |
| --- | --- |
| 内容完整、仅长度超限、客户端支持事务接收 | 无损切片交付原结果，零额外模型调用 |
| 无法无损交付，但存在明确且有预算的模型修复路径 | 最多一次短片纠错或普通 schema 修复 |
| 无法可靠修复、能力不足或预算耗尽 | 返回具体失败，保留已暂存状态，不伪报成功 |

## A：Gateway 的具体修改

### 1. 保留结构化校验事实

在 `apps/gateway/src/openai-compat.ts` 的 Ajv 校验处保留有限的结构化错误，在 `packages/core/src/errors.ts` 增加对应详情类型，并在 `apps/gateway/src/http/error-response.ts` 统一输出。

继续保留已有 `tool_call_validation_failed` 和 `schema_mismatch`，避免仅靠新增顶层错误枚举破坏旧客户端。新增 `tool_validation_contract_version: 1` 和 `tool_validation`，至少包含：

- `kind`：`content_too_long` 或普通 schema 错误。
- `tool_name`、`keyword`、`instance_path`、`schema_path`。
- `limit` 与实际字符数，按 JSON Schema 的字符计数口径记录。
- 另列 UTF-16 code units、UTF-8 bytes 和序列化参数字节数，不混用为一个“字符数”。
- `gateway_retry_attempted`、`remaining_budget_ms`、`stop_reason`。

只对明确支持的文件工具及内容字段识别长度超限：现有 write 的 /content，以及新能力下 write_fragment 的 /fragment。JSON 不完整、finish_reason=length、通用字节预算超限、未知 schema 分支不能假装成完整的超长文件。

错误响应返回给原请求客户端的受校验非正文信息可以包含目标路径，供恢复锁定原目标；日志与持久化遥测只保留诊断字段，不记录路径或文件内容。恢复前还必须确认其他参数有效。

### 2. 长度超限直接退出内部重新生成

先尝试 S 的无损交付。无损交付不可用时，在 `nativeValidationRetryPlan` 中对明确 `content_too_long` 返回“无 Gateway 模型重试”。保留已消耗 usage 与首轮 attempt；不得将未交付或未执行的失败改记成文件成功，也不得转移到另一个供应商重新生成同一大文件。

无恢复能力的请求返回原有错误码和清晰的长度信息，`transformed_retry_allowed=false`。不自动交付截短内容，也不伪造若干 write 调用。

对于能力握手完成、S 不可用但确实可进行模型修复的新客户端请求，返回 `recommended_action=write_bounded_fragment` 和 `recovery_owner=client`。只有恢复次数、剩余时间与任务状态都允许时才设置 `transformed_retry_allowed=true`。S 成功时无需先返回校验错误，也不再安排一次模型纠错。

旧客户端可能忽略新增字段，其行为必须按 beta.34 / beta.70 及实验开关开关两种状态验证。A 能保证的是 Gateway 不再启动第二次完整生成，不能仅凭响应字段保证任意旧版 SDK 从不重新提交。

### 3. 首期保留普通 schema 修复的现有行为

首期仅分流明确的文件内容长度错误。普通缺 required 字段、其他工具 schema 修复继续受现有调用次数预算、原始 deadline 与取消约束，不统一新增 120 秒准入或单次时限，不改变原 reasoning/output 参数。

```text
明确的受支持 write 内容超长 → A/S 专用分支
其他工具或非长度错误 → 原有校验修复分支与原始期限
已取消、原期限到达或调用预算耗尽 → 沿用原有结束机制
```

原因：客户端可能为短任务设置 30/60 秒期限；其中缺字段错误仍可能在数秒内恢复。强制剩余至少 120 秒会直接取消这些现有成功机会。通用预算优化须独立提交、对照测试和灰度，不能与本次长度修复捆绑。

120 秒目前仅保留为 C 的新增模型纠错候选，待其单独验收，不作为 A/S 首期通用配置。精确保留首轮失败原因的诊断可以增加，但不能借此误改其他错误的重试行为。

## B：客户端拥有顺序与文件完成状态

### 1. 复用短片段接口，不直接启用整个 Local profile

当前 `packages/opencode/src/session/local-write-fragment.ts` 已将模型输出压缩为：

```json
{
  "filePath": "report.md",
  "fragment": "本次片段内容",
  "done": false
}
```

抽取可配置的共享封装，给 goldencode 文件写入增加 `write_fragment`。不直接把 goldencode 标为 constrained，否则会同时改变本地模型专属的压缩、HTML 转换、时限和预算策略。

这是后续 B 的独立行为变更，首期 S 不启用。不得仅因客户端接受 S 就替换全部普通 write；合规小文件继续走原工具及原上限。B 的适用任务、工具替换、done 和提交状态须单独验收，确认不会把原本一次完成的普通文件无条件改成多次模型生成。

**初始灰度建议**：每片最多 4,000 个 UTF-16 code units，并同时满足实际 JSON Schema 上限和序列化字节预算。4,000 是预留余量后的保守起点，需用中英文、emoji、HTML、源码验证。不得用整体 JSON 长度代替 fragment 的长度判断。

### 2. 逻辑文件片段的序号、写入模式和哈希由客户端生成

本节专指 B 的多次模型生成。S 的传输分片由 Gateway 编号并给出源 payload 哈希，客户端重新计算核验；传输片号不占用下一次逻辑生成的片号。一次逻辑片段可对应多个传输片段。

增加客户端管理的文件写入会话，键为稳定的 `write_id`，绑定认证主体、会话、原逻辑任务和规范化目标路径；底层身份与旧 session+turn 唯一的 artifact 事务分开：

- 在请求下一片之前，先持久化待接收的 `chunk_index` 与逻辑请求身份。
- 首片对应新文件事务，后续片追加到同一事务；模型不决定 overwrite / append、序号、字节偏移或哈希。
- 同一文件只允许一个待接收的逻辑片段；未经契约标识的多个写片调用不能并行写同一路径。S 已接受的一个传输批次可以包含多个传输片，但必须先整批校验并在该逻辑片内有序暂存。
- 同一 `write_id + chunk_index` 的相同响应重放返回既有结果；内容不同则冲突失败，不能再追加一次。
- 网络重试、重复 SSE、恢复后新的 tool_call_id 都必须关联到原待接收片号，不能仅靠 tool_call_id 去重。
- 下一片只有在上一片确认暂存后才能请求；返回成功片号、累计长度和继续所需的尾部上下文。

可复用 `packages/core/src/artifact-transaction.ts` 中的暂存、偏移校验、哈希、重放检查与目标文件冲突检查。B 的本地状态及最终文件哈希由客户端对实际字节计算；S 的源 payload 哈希由 Gateway 计算、客户端复核。两者都不能要求模型生成 SHA-256。

现有普通云端 write 使用模型传入的 mode/chunk，且会直接改目标文件；不能只加一句“请 append”就认为已经实现有序且可恢复的写入。

### 3. 文件先暂存，验证后发布到目标路径

采用以下每文件状态：

```text
idle → staging → validating → committed
             ↘ failed / cancelled / conflict
```

done=false 时只暂存，不显示“文件已生成”，不发出最终 result_files。done=true 只是触发完成校验的信号；仍须确认所有片号连续、累计字节和哈希一致、没有待处理调用，并按文件类型做适当的最终校验。

在 B 的客户端管理写入模式下，完整文件校验后提交，再允许读取、运行等依赖此文件的后续工具。S 则在原一次普通 write 成功前提交。提交前检查目标修改并串行化客户端内写入；检查后再替换不能保证对外部编辑器的原子 compare-and-swap，不宣称消除了检查与替换之间的外部竞争。覆盖沿用现有文件编辑权限，不先删除原文件再 rename。

现有 ArtifactTransaction 在整个 turn 完成时才提交，且表对 session+turn 唯一、绑定旧恢复 count/owner，不能原样套到需要多文件独立提交的流程。应提取共享的校验、暂存、journal 和提交原语，新建每文件事务身份与生命周期，保持旧 artifact 协议语义，不伪装成旧 recovery_count=1。journal 还须覆盖“文件已替换、工具结果尚未持久化”间隙，重启时确认实际结果并防止二次 append。

暂存期间不对半份 HTML/源码逐片格式化，也不把部分代码的 LSP 错误误判为最终错误。格式化和最终校验在完整文件上进行，并基于最终字节更新元数据。中断后保留可恢复状态，显示“生成未完成”。

历史已写片段在发给模型的重放视图中可替换为文件状态和有限尾部，保留原始持久化会话；不得累计重复发送全部已生成文件。模型需要更多前文时通过受控读取取得。

## C：唯一恢复方、时间与次数约束

### 能力协商

S 的 write-delivery-v1、接收器 write_delivery_v1 及请求/响应契约已按 R3 确定，schema 用固定原始 UTF-8 文件 SHA 声明。B 模型短片与 C 模型纠错后续独立设计。只有实现 pre-MedcodeStream 检查与每文件事务接收并验收的 runtime 才能声明 S；native 未单独验收不得声明。开发接口冻结不意味着可在旧接收端开启能力。

现有 `chunked-file-write-v1 / artifact-completion-v1` 代码不可直接视为已接通：Gateway 当前 active chunk recovery 分支明确尚未实现；Desktop 相关路径也受实验开关控制。新能力应单独实现和验收，不依靠打开旧开关完成发布。

错误详情可复用已有 recovery_owner / transformed_retry_allowed 语义，但增加稳定 recovery_id、原请求 ID 和一次性的恢复计数。Gateway 校验恢复请求与同一认证主体、逻辑任务、原失败和已接受能力相符；多实例下也要能防止重复消费，不能只信客户端自报计数。

### 一次短片纠错

S 无法使用时，新客户端收到允许转换的长度错误后：

1. 校验原任务仍有效、尚未取消、该次长度恢复预算尚未用过。
2. 锁定目标文件，选择同一个待接收片号，不能从头覆盖已有成功片段。
3. 仅开放当前文件的短片写入工具，限制一个片段；提示“生成下一片，禁止重放整份文件”。
4. 使用明确的纠错输出预算；初始建议最多 8,192 output tokens，且不大于模型与请求的允许值。推理档位仅对该短片纠错选择已支持且通过质量验证的较低档位，普通研究请求保持用户设置。
5. 校验仍失败则结束本次自动纠错并展示原因，不启动新的 Gateway 修复、供应商切换或 SDK 通用重试。
6. 短片成功后可继续正常的下一片生成；这些是任务后续步骤，不会重新获得一次长度恢复机会。

整个逻辑任务最多一次长度纠错。客户端 `session/retry.ts` 应先处理“禁止重放/恢复已耗尽/能力未接受”，再判断实验开关；不能继续使用当前仅凭 error code 和开关决定恢复的条件顺序。

### 不重置期限

错误返回 remaining_budget_ms；Gateway 保存原截止时间，关联恢复请求仍被该截止时间约束，并原子消费恢复凭证。客户端以本地原始请求的剩余时限和服务端剩余时限的较小值准入，不能因发起新 HTTP 请求又获得 600 秒。这是 C 的待实现约束，不是当前重试计数已经具备的能力。

S 的网络接收仍用原网络期限；整响应已接收后的本地权限和提交使用客户端任务/工具期限与取消机制，二者分别定义，权限等待不重新获得模型额度。替换开始后取消需按 journal 核验真实状态，不能一律报告 cancelled 且原文件未改。

模型纠错准入建议同样从剩余 120 秒开始；单次模型纠错上限 120 秒，与原剩余期限取较小值。若 S 不可用，beta.70 案例中 505 秒的首轮失败不应再启动模型生成，beta.34 案例中 323 秒的首轮失败才可能进入短片纠错。若 S 可用，则优先直接交付原结果，不套用这个模型重试门槛。两种路径都需要客户端提交证据才能确认文件恢复。

正常分块涉及多次模型请求，还要受同一任务的已有总时限、步数及 token/额度限制约束。若目标路径没有任务级上限，启用此能力前补上有限上限；不得每成功一片或每次网络重试就重置计时和计数。

## 联调与发布顺序

1. **Gateway A**：新增错误详情、明确长度错误停止内部重试；其他错误保留原行为。验证 12,000 / 32,000 上限、短任务及旧客户端错误展示，完成后可单独灰度。
2. **Gateway S + Desktop 接收事务**：优先实现完整结果保留、无损分片与串行提交，接通能力确认；以一次模型生成完成大文件交付作为首个联合验收目标。未接受能力时保持旧接口。
3. **Desktop B + 契约 C**：完善首次生成短片、受限模型纠错及身份/次数/截止时间，完成真实客户端联调；默认先对测试账号及明确客户端版本启用。
4. 在固定灰度窗口内观察，再扩大覆盖。分别保留“Gateway 分类止损”和“新客户端自动分块/恢复”的控制开关；关闭后者不应重新开启已确认无效的超长整次重新生成。

本方案不构成发布已完成的声明。生产发布继续使用已测试的不可变提交，并按各仓库既有流程验证。

## 必须通过的验收

| 场景 | 可检查的结果 |
| --- | --- |
| beta.34 的 12,000 上限、beta.70 的 32,000 上限 | 字段与限值识别准确；Gateway 不再为确定的长度超限启动第二次完整生成 |
| 完整的 14,000 / 44,000 字符 write，仅 maxLength 失败 | 支持能力的客户端得到与原内容完全一致的文件；provider 调用次数严格为 1 |
| 无损交付时原 write 为 append 或中间片 | 保留原操作；传输分片结束不误报整个文件完成 |
| 接收无损片段中断、重复片段、payload 哈希不符 | 不提交不完整或不一致内容；重复片不重复追加；端到端失败状态明确 |
| 普通 export_document 缺 title、小工具缺字段且期限为 30/60 秒 | 保留基线中的预算内纠错机会，不被通用 120 秒门槛阻断 |
| 长度与编码边界 | 中英文、emoji、转义字符分别计算字符/UTF-16/UTF-8；工具 schema、执行端与响应详情一致 |
| 多片长 Markdown / HTML / 源码 | 最终文件与合成参考全文字节一致；无重复、遗漏、顺序颠倒或前文被覆盖 |
| 同一响应重放、不同 tool_call_id 的重试 | 同一逻辑片仅执行一次；不同内容的同片号重试明确冲突 |
| 同文件多工具调用 | 普通未声明批次阻止并行追加；S 已接受批次先完整校验再串行暂存；不得已经写入目标前片才发现后片不合法 |
| 提交前缺片、取消或断网；替换前后进程崩溃 | 未开始提交时保留原目标；替换开始后按 journal/实际摘要恢复并报告真实状态，不重复追加或虚报原文件未改 |
| 文件已提交、工具结果未持久化时崩溃 | 重启恢复同一工具结果，不再次 append；不同内容/路径/操作复用同一 delivery ID 拒绝 |
| 模型伪造封装、错误 nonce、清单摘要不符、DONE 后混合调用 | SDK 执行任何封装副作用前拒绝；不凭参数字段自证 Gateway 身份 |
| done=false 后模型直接结束 | 标记未完成，不能显示最终 result_files 或成功提示 |
| done=true 但片号缺失、目标被外部修改 | 停止提交并报告具体原因 |
| 首轮 505 秒、剩余约 95 秒 | 完整结果优先尝试受期限约束的无损交付；不能无损交付时不再启动门槛为 120 秒的模型纠错；不重置 600 秒期限 |
| Gateway 与客户端同时具备重试代码 | 一个逻辑任务最多一次长度纠错；无跨层重复恢复 |
| 能力缺失、版本不匹配、旧错误字段 | 安全退回旧接口或明确失败；不能误报已接受自动分块 |
| 写完后读取/运行文件 | 后续工具只看到已提交完整文件；权限与文件冲突检查仍生效 |

复用本次调查的 4 项隔离复现和历史 T:3XAWRBRS 用例，再补充以上状态与文件结果测试。验收不仅看 HTTP 200，还应统计首次片段交付时间、完整文件成功率、校验后 600 秒超时数、重复片段拒绝数、每任务恢复次数、最终文件校验结果和每成功任务用量。
