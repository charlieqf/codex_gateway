## 结论

在天宽 `official/glm-5.3` 的回复正文和工具参数中均独立复现了 U+FFFD（`�`）。**从上游 HTTP 响应体捕获的字节已经包含 `EF BF BD`，整个响应可通过严格 UTF-8 解码。** 当前 Gateway 适配器输出与独立解析原始 SSE 的结果一致；将同一响应重新按每次 1 字节输入适配器，结果仍一致。因此，复现样本的损坏发生在天宽返回链路，不是 Desktop 渲染或 Gateway 网络分块解码产生。

这是对同一路由、同类症状的直接复现。原客户两次调用未留存原始上游字节，不能把新样本说成那两次调用的原始字节取证；原请求的证据与复现高度一致。天宽内部究竟是模型输出、token 到文本的转换，还是中转/SSE 编码损坏，仍需供应商排查。

## Gateway 对照与处理建议

在本地及线上相同适配器上，以正常中文、标点、emoji、工具 JSON 构造 SSE，分别按 1、2、3、7 字节和完整响应分块，正文和工具参数均逐字一致。另验证上游字面 U+FFFD 会原样保留。现网 `parseOpenAISse` 使用持续 TextDecoder；本次 progress 改动没有改动这个解码器或正文拼接逻辑。实时捕获证据也不支持回滚 900 秒或 progress 改动。

当前应优先让天宽修复返回链路，并用这些固定中文样例同时验收正文和工具参数。暂不添加全局删字、猜字替换或无条件重试：这不能还原丢失字节，还可能把损坏静默写入文件或增加重复成本。两次样本均复现，不足以计算全量故障率，也不能据此断言其他供应商无问题。

Desktop 无需为本问题修改字体或编码。对已受影响任务，应让用户核对损坏的校对稿，修正后再转字幕或烧录；不能依据模型声称“复核完成”推断文件实际通过校验。如后续要增加产品层面的损坏检测，应单独评估工具参数交付前的检测与明确错误语义，不能在本次调查中静默改变执行行为。
