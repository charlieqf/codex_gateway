## 现状与节点证据

当前路径为 Gateway 全局 Node fetch → 私有 Mihomo:7890 → 海外节点 → api.x.ai。Mihomo 健康、无重启、无 OOM，无宿主机端口和控制器。配置哈希仍为 `59901802e7be8e502e15f0e7f6f672c352ffbf0f209cc56447612f2ddf4c451f`。

配置包含 32 个内嵌节点、0 个在线 proxy-provider；没有 x.ai 专用规则，日志中的 xAI 连接落到兜底选择组。现有 url-test 组使用 Google 探测地址，不能直接度量 xAI 路径健康。节点快照不自动刷新，但本次未验证任何订阅或节点到期情况。

从 9 月 11 日 00:18:25 UTC 起至本次核查，xAI 事件 200 个：159 成功、33 upstream_unavailable（本轮既有证据为响应头前 ECONNRESET）、8 客户端取消。最新真实请求于 9 月 14 日 02:26:22 UTC 成功。当前路径额外 3 次无认证 GET 返回 401（183–370 ms），3 次 HEAD 返回 401（263–313 ms）；仅证明探测时 HTTPS 路径可达，不证明图片上传和长流可靠。

## 第一阶段：筛选线路并准备小范围路由变更

1. 在独立测试进程/容器中，从受保护节点配置生成候选环境，逐条固定 B/C/A。测试不得通过切换生产全局 selector 来采样。候选配置不落入仓库、日志或外部工单。
2. 使用同一组合成图片，比较单图、8 图、较大请求体、SSE 完整读取与低并发负载；分别覆盖新建连接和连接复用。每个候选先跑约 20 次受控调用分散到多个时间段，收集握手/首字节/完整流时间、网络错误阶段与终态，作为准入样本而非长期可靠率证明。
3. 从现有资产台账及受控出口检测验证 B/C 物理线路独立性；优先选择不同提供方、不同出口 IP，条件允许时不同运营商路径。若两者共用出口，则另选独立备用线路。
4. 固定 xAI 专用组，成员直接引用通过测试的具体节点；避免成员再指向包含全部 32 个节点的自动测速或负载均衡组。正常时保持优先主出口，新连接在健康判定失败后选择备用。
5. 只增加 `api.x.ai` 精确域名规则，放在可能命中的通用规则之前。Tencent、内部服务和私有 R2 的现有直连边界保持原配置。

以下是**待绑定已验收节点的增量模板**，不是可直接覆盖生产的完整配置：

```yaml
proxy-groups:
  # 将此组追加到原有列表；两个名称须替换为受保护配置中的真实节点名。
  - name: XAI-EGRESS
    type: fallback
    proxies:
      - XAI-PRIMARY
      - XAI-BACKUP
    url: https://api.x.ai/v1/models
    expected-status: 401
    interval: 60
    timeout: 5000
    lazy: false

rules:
  # 插入原有规则列表的前部；其余规则完整保留。
  - DOMAIN,api.x.ai,XAI-EGRESS
```

Mihomo v1.19.23 的 URLTest 使用 HEAD；本次已用 HEAD 验证该 URL 无认证返回 401。因此该状态在这个**无密钥连通性探测**中表示预期应答，业务请求返回 401 仍是鉴权故障。正式验收须使用实际 Mihomo 核心跑同一探测，Node HEAD 不能代替全部代理核心测试。

现有 32 节点是内嵌 proxies，组的探测可以覆盖直接成员；以后若改为 `use` 引入 proxy-provider，需要同时在 provider 上设置健康检查，不能假设组 URL 自动覆盖 provider 成员。

## 第二阶段：业务健康判定与切换稳定性

两层探测共同判断：

- 连通层：每条候选出口每 60 秒 HEAD 一次，5 秒上限，校验 TLS 和预期状态码。与 Google 可达性分开记录。
- 业务层：定期使用合成小图进行一次真实识别，记录完整 SSE 终态；频率可从每 15 分钟一次开始，同时利用正常生产请求的被动错误统计。设置独立测试预算，并在统计中标记探针。

建议的后续健康状态机起点：连续 3 次连通失败，或近期有足够样本的业务网络错误集中出现时，将出口转为冷却；冷却 10 分钟后进入探测状态，连续 5 次连通成功且业务探针成功才重新允许主流量。具体业务错误阈值应按样本量调节，不能把一个用户反复重发当成多个独立故障。

**这些连续阈值、冷却和业务探针联动不由上面的原生 fallback 模板实现。** 原生 fallback 按可用节点顺序选择；`max-failed-times` 的含义是触发强制健康检查，不是“连续失败 N 次才切换”或“冷却 N 分钟”。第一阶段若使用原生 fallback，必须评估自动回主造成的抖动；完整状态机应在 Gateway 的出口管理中实现，或设计独立私有管理组件后另行测试。

对于有认证业务请求，401/403/429 分别归入鉴权/权限/限流检查，不以这些状态自动拉黑出口。只有证据表明路径相关的网络故障才进入线路隔离判断。

## 第三阶段：让恢复重试真正走独立出口

原生 Mihomo fallback 不能保证“一次请求连接重置后，下一次立刻走另一条出口”，也不能迁移已建立的 SSE 连接。当前 Gateway 的两次视觉调用预算已经存在，但尚不保证不同出口。

需要严格主备恢复时，新增两个仅私网可达的 xAI 代理入口 `xai-primary` / `xai-backup`，分别固定经过验收且相互独立的主、备线路。

Gateway 对 xAI 使用独立 dispatcher/连接池，按每次上游 attempt 选择代理入口：初次主出口，符合现有视觉恢复条件时第二次备用出口。该能力需要代码与隔离故障测试，不能宣称改一个 Mihomo 组就已实现。

保持现有合同：单个 Gateway 模型请求中，初次、工具纠错与失败恢复合计最多两次；共用总期限，取消即停止，已输出正文或工具片段后不透明重放。切换仅影响新尝试/新连接，不强制终止其他在途 SSE。响应头前重置也不能保证 xAI 从未接收请求，仍需保留调用计数与费用观测。

每次记录 request ID、attempt 序号、实际代理入口 alias、路由配置版本、网络错误阶段和恢复结果。若仍有动态节点选择，必须区分“选择的策略组”与“实际节点”，不能用读取 selector 的瞬时值冒充该请求的实际出口。

## 验收、发布与回滚

- 在实际 v1.19.23 核心上验证增量配置和行为；仅语法解析成功不足以证明字段生效。
- 在隔离环境验证主出口断连、备用接管、备用也失败、恢复回主、取消和部分输出断流，观察实际节点与调用次数。
- 形成具体节点映射、配置 diff、受保护备份及恢复步骤后，按生产变更流程部署。现有容器未配置控制 API，不使用不存在的 9090 selector 接口，也不临时公开该端口。
- 生产切换安排在低流量窗口，先处理在途视觉请求。仅改变目标代理服务/路由配置，并验证 Tencent、R2、Gateway 公网健康和原有安全边界。
- 小范围验证后观察 24–48 小时，报告样本量、独立 turn 的首次网络失败率、恢复成功率、最终失败率、完整流耗时和实际出口分布；零流量不算恢复证据。
- 若出现新连接失败或其他海外路径退化，恢复已验证的受保护旧配置与必要选择状态，重新验证健康；不修改用户 key、模型权限或全局 NO_PROXY 作为代理回滚手段。

本轮没有执行候选线路真实图片压力测试，没有选定可直接投产的独立主备组合，也没有改变生产。下一步可执行交付是 B/C 候选线路对照测试、独立性核实、最小路由 diff 和回滚包。
