# GoldenCode 腾讯／天宽双向故障切换实施方案

日期：2026-09-07。状态：代码已实施并部署，P0 已启用、P1 未启用。本文保留设计依据；
实际实现见[实施记录](./goldencode-failover-implementation-2026-09-07.zh-CN.md)，
线上配置与验证见[发布记录](./goldencode-failover-release-2026-09-07.zh-CN.md)。
按用户后续指令，生产天宽已暂停，当前只启用腾讯，见
[天宽暂停记录](./goldencode-tiankuan-suspension-2026-09-07.zh-CN.md)。

## 1. 目标与责任边界

由 Gateway 在同一个客户端请求内完成腾讯与天宽之间的受控切换。客户端继续请求
`goldencode`，不选择供应商，不接触供应商密钥，也不承担平台切换策略。

目标行为：天宽返回额度不足、限流或可恢复服务错误时，如果本请求尚未向客户端
交付业务输出，Gateway 尝试腾讯；腾讯发生同类故障时可以反向尝试天宽。两个平台
都失败则返回一次明确的终态错误，不在平台之间循环。

本次范围：

- `goldencode` 文本池中的 `tencent / glm-5.3` 与 `tiankuan / official/glm-5.3`。
- 普通文本与原生客户端工具调用，覆盖流式和非流式 Chat Completions，以及复用
  `executeChatCompletion` 的 Responses 兼容入口。
- 供应商错误分类、尝试预算、冷却、观测与计量一致性。
- 客户端的请求生命周期、错误展示、关联诊断和恢复协作。

不扩展到 xAI 视觉、GoldenCode Local、图片生成或 Research 独立执行链。
尤其不能把 xAI 视觉失败直接切入不具备相同视觉能力的文本池。
本方案也不修改用户套餐、额度或计费政策。

## 3. 分阶段交付

| 阶段 | 交付内容 | 退出条件 |
| --- | --- | --- |
| P0 | 原生工具路径双向切换、统一预算、错误与用量记录、完整回归 | 故障注入下，两平台方向、两种响应模式及两个 API 入口通过；只交付一个最终结果 |
| P1 | 额度专用冷却、单请求恢复探测、防并发误恢复 | 小请求成功不解除业务额度故障；同一故障范围只放行一个恢复探测 |
| 客户端配合 | 避免叠加重试、取消传播、清晰终态、诊断上传 | 已安装客户端中切换成功无错误闪烁，失败可关联到 Gateway request ID |

P0 可以先沿用现有冷却，改善单次请求成功率；在 P1 完成前，必须明确仍可能有
周期性首跳失败和额外延迟，不能宣称已经具备完整的额度熔断能力。

## 4. Gateway 执行设计

### 4.1 共用执行函数

建议新增 `services/native-tool-failover.ts`，由流式和非流式原生工具分支共用。
函数接收当前 `ChatRuntimeContext`、原始请求、总截止时间、取消信号、尝试预算和
现有原生工具执行回调，返回最终运行态、结果／错误、全部尝试摘要。

依赖现有 dispatcher 选择候选平台，不在工具逻辑中写死供应商名称。`index.ts`
负责 HTTP/SSE 输出与最终结算；该函数负责平台尝试，保持职责可测试。

```text
请求完成鉴权、准入、一次预算预留
  → 获取平台 A 的 lease
  → 执行一次上游调用
  → 成功：校验完整结果，交付一次
  → 失败：保存摘要，记录 A 的故障
      → 不满足切换条件：终态错误
      → 满足：释放 A，排除已尝试成员，获取 B 的 lease
          → 没有合格 B：终态错误，保留 A 的故障原因
          → 有 B：更新运行态观测，重建 B 的供应商参数，执行
              → 成功：只交付 B 的结果
              → 失败：终态错误
  → finally：释放当前 lease、结束活跃请求、结算一次、写一条请求事件
```

切换的是当前模型轮次。原始上下文包含此前已经完成的工具结果；不能重跑历史
Shell／write，也不能把 A 的半截文本或工具参数拼入 B 的答案。

每个获得的 lease 必须恰好释放一次。成功切换后，活跃请求和最终 provider 归属必须
指向 B；尝试历史仍保留 A。获取 B 失败、异常抛出、取消和超时都需要覆盖资源释放。

### 4.2 切换资格

引入明确的内部判定函数 `canFailover()`。不能只依据公共 `error.code`，更不能把
所有 401、402、429 一律当作供应商故障。

| 条件／故障 | P0 决策 |
| --- | --- |
| 供应商来源的 402，包含天宽额度不足 | 允许切换并记录额度故障 |
| 供应商 429、5xx | 允许切换；记录适用的冷却／Retry-After |
| 响应头前的连接重置、连接失败 | 允许切换；保留真实网络失败阶段 |
| 上游自身超时，但 Gateway 总截止时间尚未到达 | 有足够剩余时间时允许切换 |
| Gateway 用户套餐／额度拒绝、认证失败、请求限流 | 不切换，保留原准入错误 |
| 客户端取消、下游断开、Gateway 总截止时间到达 | 不切换，终止上游工作 |
| 参数错误、上下文超限、输出长度耗尽、工具参数校验失败 | 不触发跨平台切换，保留现有专门恢复契约 |
| 内容策略拒绝 | 不切换 |
| 已经生成部分内容后才发生流中断／协议异常 | P0 不扩展此类跨平台重放；保留现有处理，后续单独设计 |

必须同时满足：

1. 当前运行态属于本次启用的双平台池，候选平台支持相同工具及请求能力。
2. 尚未向下游交付文本、推理增量或工具调用等业务输出。
3. 请求未取消、连接未关闭、总截止时间未到、实际调用预算仍有剩余。
4. 失败属于本次明确允许的类别；不能由工具参数错误进入供应商故障切换。

流式响应可能已发送 HTTP 头或 SSE 心跳，因此不能用 `headersSent` 判定是否可切换。
应维护明确的 `businessOutputCommitted` 状态，成功写出第一块业务输出时置位。
原生工具路径保持完整收集、校验后再交付的行为；内部已生成内容不能冒充已交付。

`before_headers` 仅说明 Gateway 未收到响应头，仍可能发生在请求已到达供应商之后。
不得据此声称供应商未执行或不会计费。

### 4.3 调用预算与超时

对启用 P0 的双平台原生工具路径，使用请求级共享预算，最多两次实际模型调用。
跨平台切换和现有参数修复、空回复恢复等附加模型调用共用该预算。
预算应在真正发起 adapter 调用的位置扣减，不能只在外层循环计数。

| 实际顺序 | 是否允许再调用 |
| --- | --- |
| A 首次调用 402 → B 成功 | 已用两次，不再调用 |
| A 首次返回需修复的工具参数 → A 修复 | 已用两次，修复失败不再转 B |
| A 首次连接失败 → B 返回需修复的工具参数 | 已用两次，返回明确校验错误，不再修复 |

平台切换使用原始请求，参数修复继续使用现有修复上下文；两者不得混用。
未启用的其他模型路径不因本次修改而改变其既有修复次数。

两次调用共享原请求的绝对截止时间和取消信号。B 仅能使用剩余时间；不能在切换时
重新获得完整超时。如果 A 已消耗整个 Gateway 截止时间，立即结束。
P0 不通过全局缩短首跳超时来人为制造切换机会。

### 4.4 参数和能力一致性

- 保留原始消息、图片／工具结果引用、工具定义、`tool_choice`、输出上限与用户显式推理等级。
- 通过目标 adapter 重新构建供应商请求，使用目标模型的参数和默认推理配置。
- 校验 B 的上下文和输出能力；不支持则不选用，不静默裁剪上下文或降低输出上限。
- 不为规避天宽额度问题把用户请求的 `max_tokens` 自动改成 256。
- 同一轮只交付成功平台的完整工具调用；不复用失败平台尚未交付的工具调用 ID 或参数。

## 5. 错误分类和供应商关联标识

在 OpenAI-compatible adapter 的错误处理处保留：供应商、真实 HTTP 状态、错误类别、
失败阶段、transport code、供应商 request ID。客户端收到的错误仍遵循公共契约，
不直接透出账户、余额、供应商原始响应或密钥信息。

402 分类必须有供应商来源证据。内部可标记为 `provider_quota_exhausted`，名称在实现
时与现有类型系统统一；这是建议的内部分类，不表示已有公共错误码。

从已批准响应头和错误 JSON 顶层 `request_id` 提取供应商标识，验证类型、长度并脱敏。
例如天宽实际错误 JSON 内有编号，而标准事件的 `upstream_request_id` 为空，需要补齐。
只保留支持定位所需字段，不把完整供应商响应写入普通日志。

供应商错误与“没有可用备选平台”分别记录。若 B 未执行，不能伪造第二次上游尝试；
最终错误需保留 A 的原因及未切换原因，避免用泛化的池不可用覆盖诊断证据。

## 6. 最终状态、用量与计量

维护两个明确视图：

- **最终结果**：请求成功／失败、最终平台、最终错误、实际交付内容和工具。
- **全部尝试**：按顺序记录每次供应商调用、耗时、错误、用量和切换原因。

示例：天宽 402 后腾讯成功，最终 `request_events.status=ok`、最终公共错误为空；
尝试数组保留天宽 402 和腾讯成功两条记录。不能因历史 402 把最终请求标成失败。

使用现有 `combineProviderStreamSummaries()` 时，应增加明确的最终结果投影，或使用
单独的合并入口。不要未经审查全局改变其历史失败保留语义，以免影响其他调用方。
区分“全部尝试产生的内容字符数”与“实际交付字符数”，不能以汇总字符数证明交付。

计量要求：

1. 一个客户端请求只做一次准入、预算预留和最终结算；切换不再次扣请求次数。
2. 每次上游返回的实测 usage 单独保留并准确汇总，不重复相加。
3. 失败尝试没有 usage 时保留缺失／估算来源，不伪造实测零用量。
4. 供应商实际成本与用户账单分别遵循现有政策，不因增加切换而隐式改变收费规则。
5. 取消、超时、B 不可用时也必须释放所有预留和并发占用。
6. HTTP/SSE 响应 usage、请求事件和权威用量账本必须一致；明确验证后续
   `markOpenAITokenUsage()` 不会用 B 单次用量覆盖已经合并的用量。

保持同一个 Gateway request ID、客户端 turn/message/session ID。内部尝试增加连续
序号及 `failure_retry` 目的标记，避免与工具参数修复混淆。支持码是关联标识，不是
自动具备去重语义的幂等键。

## 7. P1：额度故障冷却与恢复

额度不足与短暂服务故障分开处理。建议先以“池成员＋账户”为保守故障范围，使用
独立可配置冷却；初始参考值为 5 分钟，需结合供应商规则和生产流量验证。
如果同一企业余额跨多个密钥共享，确认后再扩大故障范围，不能凭猜测全局封禁。

状态转换：健康 → 冷却 → 单探测恢复 → 健康／再次冷却。

- 冷却期间正常业务直接选择另一个合格成员，保留会话粘性策略但跳过故障成员。
- 冷却结束只放行一个恢复请求，其余请求继续走健康成员，避免并发冲击。
- 恢复请求需覆盖约定业务输出预算，并考虑输入规模；256-token 小探针通过不能
  清除曾在 4,096／128,000 上限触发的额度故障。
- 可使用严格短答案提示配合业务输出上限做有成本上限的恢复探测；需设频率和预算，
  不启动无界长输出测试。即使通过，也不能保证任意更大输入都可用。
- 若采用不同请求规模分级恢复，需要显式维护准入档位；P1 首版可采用保守成员级冷却。
- 使用故障代次／状态版本，故障前已在途的旧成功不能清除新冷却；只有当前恢复
  探测的结果可以完成恢复。探测被取消或结果不明时不得标记健康。
- 明确状态存储范围：现有进程内冷却在重启后丢失。P1 若要求跨重启保留，应采用
  最小状态持久化并验证恢复，不能把进程内状态描述成全局或持久熔断。

额度失败状态、恢复探测时间和结果对运维可见；普通产品界面不展示供应商账户信息。

## 8. 客户端配合优化建议

### 8.1 请求生命周期和重试

客户端只请求 `goldencode`。Gateway 在请求内切换时，客户端保持同一轮“处理中”，
不创建新消息、不重复提交、不短暂显示第一次供应商错误。

- 审查 SDK 隐式重试与客户端外层重试，避免一次点击触发多层重试，放大供应商调用。
- 同一轮只允许一个活跃提交；连续点击“继续／重试”应去抖并序列化。
- 传入稳定的 turn/message/session ID 和客户端版本，每次新 HTTP 尝试保留自己的
  Gateway request ID；记录重试原因及前序请求 ID。
- 不把复用 message ID 当作 Gateway 已实现持久幂等。未提供去重／结果查询契约前，
  网络结果不明时不能自动声称重放是安全的。
- 用户取消后立即传播 AbortSignal，停止本地重试；不能随后又静默重启该轮。
- 客户端超时应依据已发布的 Gateway 总期限契约配置，并给终态传输留余量；不为
  支持双平台切换简单把总超时翻倍。设置项与最终数值需双方确认。

### 8.2 错误展示和恢复操作

| 最终情况 | 建议展示／动作 |
| --- | --- |
| Gateway 内部切换成功 | 正常展示一个答案或一组工具调用，不显示已恢复的中间错误 |
| 两个平台均不可用 | 显示服务暂不可用及支持码；有可信 Retry-After 时尊重等待时间 |
| 已收到部分回复后连接中断 | 保留已有内容，标记未完成，提供明确的继续／重试入口 |
| 工具参数截断、输出耗尽 | 按错误契约执行分段生成或继续，不能归为供应商认证失败 |
| 本地 write／Shell 失败 | 单独展示本地工具错误，保留工具调用 ID，不触发平台切换 |
| MedEvidence 密钥验证失败 | 单独检查密钥解析与服务入口，不能混入模型平台故障提示 |

工具执行状态应可关联、可持久化。只有已经完整接收、校验并确认可执行的工具调用
才执行；恢复时检查本地完成记录，避免重复写入或执行。不能承诺仅凭一个工具 ID
就能实现跨崩溃的“恰好一次”执行，需要结合真实持久化和副作用边界验证。

### 8.3 诊断上传

至少记录：app version、turn code、session/message/tool-call ID、Gateway request ID、
请求开始／结束／取消时间、是否收到业务输出、最终错误码、恢复动作和本地工具结果。
不上传原始工具参数、全文、完整密钥或带签名资源 URL。

启动上传失败、队列积压、上传被认证拒绝需要可观测，不能静默丢失。验证重启后
诊断队列恢复，并保持有界重试与保留策略。本次排障已发现“消息持续上传而工具
诊断长期缺失”的情况，因此不能只测试消息上传通道。

客户端增强不应成为 Gateway P0 生效的前提；旧客户端仍须收到兼容的成功／错误响应。
如果确需新增公共错误字段，先定义可选字段、兼容行为和契约测试，再协调客户端。

## 10. 验证矩阵与验收标准

自动测试使用本地可控的 OpenAI-compatible 上游服务器注入故障，不通过真实生产
供应商故障来制造测试条件。每个方向覆盖流式／非流式及原生工具路径。

| 场景 | 必须验证 |
| --- | --- |
| 天宽 402 → 腾讯成功；腾讯 429 → 天宽成功 | 一次客户端请求，两个正确归属的 attempt，只交付一个成功结果 |
| A 5xx／响应头前 reset → B 成功 | 分类和切换原因正确；同一总期限 |
| A、B 均失败 | 最多两次真实调用，一次终态错误，原因可追溯 |
| B 冷却／禁用／无并发容量 | 不调用 B，不伪造 attempt，A 的原因不丢失 |
| A 返回错误前／切换期间用户取消 | 不再发起 B，lease 和预留完全释放 |
| 总截止时间已到／剩余时间不足 | 不重新启动完整超时，不启动无意义的下一次调用 |
| 已交付业务输出后失败 | 不跨平台重放，不产生重复工具调用或混合文本 |
| 已有历史工具结果 | B 获得原上下文；客户端只执行本轮最终新工具调用 |
| 需要工具参数修复 | 修复与切换共享两次预算，所有真实调用都记账 |
| 参数错／上下文超限／截断／策略拒绝 | 不进入本次跨平台路径，专门错误契约保持一致 |
| Gateway 自身套餐 402、认证 401、请求限流 | 不调用任一上游，不误触发供应商冷却 |
| 失败后切换成功 | 顶层成功；历史失败仍在 attempts；usage 不覆盖、不重复 |
| 失败尝试 usage 缺失或已有部分实测 usage | 保留来源，最终账本与响应契约一致 |
| 错误 JSON 含供应商 request ID | 保存编号；不保存密钥和完整响应 |
| Responses 流式与非流式 | 与 Chat Completions 相同预算、状态、取消和输出语义 |
| P1 并发恢复／旧请求晚到成功 | 单探测；旧结果不能解除新冷却 |
| P1 小请求通过、大预算失败 | 不把小请求成功视为业务额度已恢复 |
| 开关关闭及非目标模型 | 既有路径行为不变 |

实施后的本地检查建议：先运行相关 Vitest 文件及 `npm run typecheck`，再按仓库实际
发布门禁补齐 Gateway、provider-stream、Responses、计量和路由回归。
这是待执行清单，本文编写时未执行代码测试。

客户端验收需使用实际安装包：故障注入代理／测试环境中验证切换成功无错误闪烁、
两边失败只显示一个终态、取消不重启、工具不重复执行、诊断可以完整关联。

## 11. 发布、观测和回滚

建议新增默认关闭、仅作用于目标池的 native failover 配置开关；确切名字在实现中
登记到配置文档。调用硬上限保持 2，不提供无界重试配置。P1 冷却策略独立开关。

上线顺序：

1. 核对 R760 当前发布与工作树，隔离已有变更；从测试通过的不可变提交构建。
2. 在隔离环境完成上述矩阵，再进行有上限的两供应商真实短请求验证。供应商仍有
   额度故障时如实记录，不靠反复请求刷出一次成功作为验收。
3. 经发布授权，建立并验证变更前备份，检查密钥文件权限；仅部署 Gateway，遵循
   [Container Deployment](./container-deploy.md) 与 R760 overlays。
4. 从受控测试身份逐步启用目标路径。若配置不支持按身份灰度，先实现明确灰度能力，
   不把全量开关称作灰度；按阶段检查观测后再扩大范围。
5. 验证公共健康、容器重启、SQLite 完整性／外键、请求与 usage 记录，以及临时
   测试用户、凭据、预留和文件清理。
6. 完成客户端安装包协作验证后，记录上线版本、时间、开关范围和实际测试请求 ID。

观察至少包括：每平台首跳错误数、独立受影响 turn 数、切换次数／成功率、实际调用
次数、最终错误率、P50/P95 总延迟、usage 缺失率、冷却与恢复事件。
将上游尝试错误率与客户端最终失败率分开，不能让成功切换掩盖供应商持续故障。

以下情况立即停止扩大并回滚开关：重复工具交付、调用超过硬上限、取消后新发请求、
预留／并发泄漏、计量不一致、切换成功被误标失败。可用性和延迟的数值门槛应依据
上线前基线确定并写入发布记录，不能临时挑选有利窗口。

关闭 P0 开关后恢复原路径；若需回滚二进制，回到已经验证的上一不可变发布。
P1 涉及持久状态时需确保旧版可读取或忽略，避免代码回滚被 schema 阻断。
不通过重启 Tencent、TianKuan 外部服务或修改客户端密钥来实施该回滚。
