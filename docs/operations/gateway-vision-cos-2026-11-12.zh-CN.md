# Gateway 图片存储迁移至腾讯 COS：本地实现与验证

状态：2026-11-12 已完成本地实现和真实存储/天宽小样本验证，尚未部署、推送或发布客户端。本文不代表已切换生产流量。

## 原因与目标

2026-11-11 15:47:50–15:48:01（北京时间），天宽 deepseek-v4.1-flash 在 HTTP 200 建立流后返回图片下载超时、错误码 400，没有模型输出。上游请求 ID 为 `e1711c47-dce0-4432-bc7a-2bcc43160c76`。客服说明图片抓取存在约 10 秒限制，跨境访问 R2 会增加失败风险。

使用独立上海桶 `gateway-vision-1354744323`（`ap-shanghai`）存放短期识图图片，不与 RTI 的会议归档桶共用目录或凭据。保留原图，不通过有损压缩牺牲文字、图表和医学图片细节。

## 无需所有用户同时升级

Gateway 在创建上传授权时，检查请求头 `x-medcode-vision-storage: cos`。未声明能力的客户端继续获得原有 R2 域名、`va1` 资产 ID 和上传头；新版客户端可以获得 COS 域名、`vc1` 资产 ID 和 COS 上传头。后续完成、续签和删除按资产 ID 选择原存储，再校验所有者和签名，不对认证失败进行跨桶重试。

| Gateway 配置 | 旧客户端（无能力头） | 新客户端（声明 COS） | 已有资产 |
|---|---|---|---|
| 旧 Gateway / R2 | R2 | R2，旧服务忽略能力头 | 保持原行为 |
| 新 Gateway / COS，保留 R2 配置 | R2 | COS | `va1` 读 R2，`vc1` 读 COS |
| 新 Gateway / 切回 R2，保留两套配置 | R2 | R2 | 仍可读取、续签和删除两类资产 |

因此上线顺序可以是：先部署兼容 Gateway，再逐步发布和升级客户端。只要还有旧版使用者，就不能关闭 R2 上传。COS-only 配置无法服务旧客户端的图片创建，会明确返回 426；这不是本次混合版本上线方案。

**已确认范围：旧客户端继续使用 R2，新客户端支持 COS，逐步升级。** 用户于 2026-11-12 明确认为旧版立即受益不紧迫，应避免为此引入额外缺陷。因此本次不做 R2→COS 透明转存，也不将其列为上线前条件。旧版仍保留原跨境抓图风险；不会改变其读取 URL、后台迁移图片或新增跨桶失败重试。

## 实现与安全边界

- Gateway 新增 `CosVisionStorage`，使用 COS XML 签名；没有将 COS 当作 R2 的 AWS SigV4 端点。
- 上传强制 `x-cos-forbid-overwrite: true`、`x-cos-server-side-encryption: AES256`，并签入内容类型及 SHA-256 元数据。完成接口实际下载、校验大小、格式和完整 SHA-256 后才写 ready 标记。
- 图片客户端 PUT 不额外宣称带 Content-MD5；现有接口只有 SHA-256。Gateway 自行上传的 ready 标记带 Content-MD5。SHA-256 完整验证覆盖最终图片字节。
- 资产 ID 绑定账户；COS ID 还绑定桶端点。读取签名仅限 GET，续签不延长资产本身有效期。
- 指纹支持 COS 签名续签，迁移期保留原 R2 派生观测密钥；诊断隐藏 COS 签名和资产 token。
- Desktop 源码位于 `C:\work\code\medevidence-opencode-stable`，增加 COS 能力头、URL/上传头兼容、409 幂等确认、续签与回收 ID 识别、会话引用保护和诊断脱敏。完整保留 R2 行为。
- 两种存储的资产元数据和原图恢复流程保持原有效期语义；客户端二进制降级前需考虑新版已产生的 `vc1` 本地记录，不能假定旧客户端可读取它们。

## 配置与回退

COS 凭据只供 Gateway 使用，四字段 JSON 为 `bucket`、`region`、`secretId`、`secretKey`。本机文件位于仓库外的受限目录，凭据不进入 Git、客户端或诊断日志。生产挂载应只读，并遵循现有 secret 文件权限校验。

```dotenv
MEDCODE_VISION_STORAGE_PROVIDER=cos
MEDCODE_VISION_COS_CREDENTIALS_FILE=/run/secrets/gateway-vision-cos.json
# 原有 MEDCODE_VISION_R2_* 配置保持可用，供旧客户端和 va1 资产使用。
```

默认上传 URL 600 秒、读取 URL 1800 秒、资产 86400 秒、存储请求超时 30000 毫秒。COS 可使用 `MEDCODE_VISION_{UPLOAD_URL_TTL_SECONDS,READ_URL_TTL_SECONDS,ASSET_TTL_SECONDS,REQUEST_TIMEOUT_MS}`；未设置时继承对应 R2 配置，再回落到默认值。

回退新上传目标时，在保留此兼容版本及两套凭据的前提下设 `MEDCODE_VISION_STORAGE_PROVIDER=r2`。这样新上传回到 R2，尚有效的 COS 资产仍可访问。不能直接回退至完全不识别 `vc1` 的旧 Gateway 二进制而宣称图片无损兼容。

管理员应保持桶私有、标准存储、关闭版本控制，配置 `vision-temp/` 的短期生命周期清理，建议修改后 2 天清理、应用资产 24 小时过期。清理是异步的，不等于严格定时物理删除。当前对象级凭据不能完整读取桶的生命周期/版本控制配置，仍须由管理员核对；已通过实际重复 PUT 验证当前对象不可覆盖。

## 2026-11-12 自审与修正

审查范围为本次 COS 接入的 Gateway 与 Desktop 源码、配置示例和测试；没有审查或提交其他任务已存在的工作区修改。用户已明确排除旧版透明转存。

发现并修复：

1. **P2，客户端上传主机校验回归。** `vision-storage.ts` 原先匹配原始 URL 正则；包含反斜杠的伪 R2 地址可匹配成功，但 `URL` 解析结果指向另一主机。现按解析后的 URL 校验，并收紧供 SDK 使用的域名正则。测试先复现误判，再验证上传前拒绝，图片字节不会发出。
2. **P2，COS 图片内容指纹错误合并。** `request-payload.ts` 原先删除全部查询参数，版本号或裁剪参数变化也被当作同一张图，可能把用户实际缩小图片的重试误判为未缩减。现仅剥离 COS 授权字段，保留版本和转换参数；保留既有 R2 指纹语义。三种内容选择参数的失败测试已转为通过。
3. **P3，缺省客户端能力偏向 COS。** HTTP 路由原本会明确传递能力，但双存储服务的内部 API 在省略能力参数时默认 COS。现只有明确支持 COS 才分配 COS，其余走 R2；缺少 R2 时按已有配置返回升级要求或存储不可用，不偷偷转换图片。
4. **P3，签名的编码路径边界。** COS 规范使用解码后的对象路径参与签名，原实现使用编码路径。当前系统的 ASCII UUID 对象名不受影响，但含空格、括号或非 ASCII 字符的路径会产生错误签名。已按[腾讯签名规范](https://cloud.tencent.com/document/product/436/7778)修正，并使用独立 Python HMAC 计算的固定样例验证。

代码质量改进：双存储路由明确命名为 COS/R2，减少主次概念和重复分支；配置验证返回明确字段并复制为私有只读配置，避免外部对象修改影响后续签名；COS 凭据路径在存储与指纹初始化中一致去除首尾空白；测试存储状态按桶和对象隔离，验证删除 COS 不影响 R2。遍历查询参数时先保存名称集合再删除，避免跳过相邻授权字段。

修复后首轮检查：Gateway 7 个文件、138 项测试通过；Desktop 8 个文件、151 项测试通过；两仓类型检查通过。最后补充相邻/重复签名参数边界后，Gateway 指纹 7 项、Desktop URL/指纹/上传 47 项定向复测通过，不与前一轮累计计数。静态检查无错误，既有整文件扫描仍有风格/类型提示，不宣称全仓 lint 无警告；本次 URL/指纹模块及对应测试 4 个文件单独检查为 0 警告、0 错误。没有发布安装包、改变生产配置、转存旧图片或重新执行付费模型测试。
