## 一、发布排空：线上事故成立，并发现关联的结算缺陷

### 1. 已发生的发布中断

09-28 发布切换开始于 **03:02:36.320257**，新容器启动于 **03:02:41.240972561**。Nginx 在 **03:02:40–42** 记录 10 次 502：模型 2、诊断 7、credentials/current 1。错误包含 1 次 upstream prematurely closed、8 次 recv failed、1 次 connect failed。

发布脚本只轮询 `token_reservations WHERE finalized_at IS NULL`，看到零后执行单容器强制重建。检查期间没有关闭新任务准入，计数也不包含全部 HTTP 和后台工作。[脚本](../../scripts/ops/r760-gateway-release-20260923-cutover.py)

在排空检查结束、进入切换之后，生产确实又创建了预留：

| 字段 | 值 |
| --- | --- |
| request ID | `req-8de0d045-e84c-4447-920a-5c5e1a159e0f` |
| 创建时间 | 03:02:39.231 |
| 到期时间 | 03:07:39.231 |
| 最终结算时间 | 03:07:43.455 |
| 最终用量来源 / 总数 | estimate / **62,827 Token** |
| 对应 request_events | 没有找到 |

这证明切换窗口仍接收了新模型工作，并留下缺少完成事件的估算结算。它与中断时间吻合；现有日志不能确定上游是否已执行、执行多少，也不能把这条记录精确对应到某一个 Nginx 502。

这条记录 `entitlement_id` 非空、`free_entitlement_id` 为空，`final_free_tokens`、`final_paid_tokens` 均为 0。**62,827 是 Gateway 用量账本的估算记录，不能直接表述为现金扣费、月付/年付扣款或已确认应退款数额。** 应先核对权益窗口与上游用量；本次没有调整它。

### 2. 即便关闭新准入，“未结算预留为零”也不等于任务完成

预留期限固定为 5 分钟；其他请求触发到期清理时，会把仍未结算的预留按缺失用量策略结算。后续 `finalizeReservation` 发现已经结算，直接返回旧结果，实际 provider 用量不能覆盖估算值。

源码位置：[预留和结算](../../packages/store-sqlite/src/token-budget.ts) 的 `acquire`、`cleanupExpired`、`finalizeReservation`、`finalUsageForRow`；[请求清理入口](../../apps/gateway/src/index.ts) 的 `cleanupExpiredTokenReservations`。

固定窗口中有两笔已确认的长请求在模型完成之前被清理：

| request ID | 时长 | 预留到期 → 结算 | 账本估算 | 请求事件实际用量 | 差值 |
| --- | ---: | --- | ---: | ---: | ---: |
| `req-3f3b0567-b2a4-4245-a9f0-1ece5e153c25` | 383.847 秒 | 02:35:12.808 → 02:35:18.268 | 86,434 | 81,716 | +4,718 |
| `req-70cec368-3dfa-4cb0-8e83-dbdc8ea05eda` | 323.653 秒 | 07:56:46.416 → 07:56:49.520 | 112,708 | 107,144 | +5,564 |

第一笔在本次发布前发生，第二笔在发布后发生，不能归因于新回执 migration 36/37。其他超过 300 秒的请求可能抢先用实际用量结算，因为清理依赖后续请求触发，并非到第 300 秒立即运行。

离线用真实 SQLite limiter 复现：预留 125，301 秒执行清理，未结算数变成零；380 秒提交实际用量 110，最终仍为 estimate/125。这也证明该 SQL 计数无法作为发布排空条件。

### 3. 应用关闭与多实例的限制

- 启动入口没有 SIGTERM/SIGINT 调用 `app.close()` 的处理；已有 `onClose` 清理不代表进程信号会触发它。Docker `init=true` 不能代替应用排空。运行链为 docker-init → npm → sh → Node。
- health readiness 没有 draining 状态。生产 Nginx 对此域名只有 `127.0.0.1:18787` 一个后端。只改 readiness 响应，现有静态转发不会自动完成切流。
- 普通请求、诊断等限流状态在进程内；直接多开副本会改变总准入量。
- 模型回执使用进程 owner 和本地活动集合。双实例共享同一离线 store：原实例查询为 running，另一实例查询为 unknown；同 ID 重提返回 `409 model_call_unconfirmed`，**仍只有一次执行**。完成后第二实例可以查询 completed。因此不能声称多实例必然重复执行，但现有运行中查询语义不适合直接轮询负载均衡。

### 4. 修复方向与验收

1. 用显式、不可竞态的新任务准入开关开始 drain，并单独统计实际执行中的模型、图片后台工作及其他需保留的操作；HTTP 连接关闭、预留已结算都不等同于后台工作结束。
2. 接入应用信号处理、关闭顺序、最长等待及超时审计；部署脚本必须调用并核实 drain，再停旧进程。单实例期间明确返回可识别的 503/Retry-After，不能承诺零拒绝；查询等控制接口按关闭阶段处理。
3. 预留增加可验证的执行存活/租约机制与执行期限，区分活跃工作和真正孤儿；实际用量迟到时需要幂等、可审计的差额更正，覆盖相关权益窗口及并发结算。单纯把 5 分钟调长只能缓解，不能建立正确性。
4. 对上面三笔做独立用量核对，不批量把缺失用量策略改为零，也不在缺少权益及上游证据时直接退款。
5. 要实现连续服务，再设计 owner 感知路由或共享执行租约、跨实例资源上限和迁移兼容；不要直接开启模型 POST 的代理自动重试。

验收至少覆盖：drain 边界恰好有新请求、正常长 SSE 超过 5 分钟、客户端断开但后台未停、孤儿回收、迟到用量多次上报与并发上报、关闭期限用尽、重启恢复。必须同时核对执行次数、结果、预留/权益账本和边缘状态码。

## 二、诊断上传：客户端重试问题与 Gateway 预算缺陷同时存在

### 1. 当前真实协议及计数口径

- 线上配置为 **60/min、2,000/day**。限流 key 是 credential + family；messages 与 diagnostics 是独立桶，且不占普通模型请求桶。
- v1 每个 HTTP 请求只接受一个事件，body 上限 256 KiB、metadata 上限 192 KiB，没有批量协议。
- 在解析、查询重复事件之前计入请求预算。因此同 event ID 重发返回 200 仍耗预算；通过准入后返回的格式错误或内容冲突也耗预算；被拒绝的 429 本身不增加计数。
- 是按 UTC 固定窗口的内存请求计数，进程重建后丢失；不能描述为持久的“每天最多保存 2,000 条唯一事件”。

对应源码：[diagnostics 路由](../../apps/gateway/src/index.ts)、[事件解析](../../apps/gateway/src/services/client-event-ingest.ts)、[限流器](../../apps/gateway/src/services/rate-limiter.ts)。

离线把日额度设为 3，同一事件三次结果为 201/200/200，计数为 3，随后不同的终态事件被 429 拒绝；换一个 limiter 实例又能准入。这是请求防护的现有行为，不能误称去重失效：事件没有重复保存，预算仍被消耗。

### 2. 线上两种不同问题

**beta.78 关联流量：** 12:41–12:42 共 52 次诊断 429。12:41:41 返回 Retry-After=19 秒，仍有 45 次拒绝发生在该分钟内，其中首秒 9 次。这证明冷却期内仍有请求到达。版本通过凭证及邻近已接收事件关联；被拒绝请求体未保存，不能断言 52 次全由同一个进程或具体某段队列代码产生。客户端应核查跨 main/sidecar/队列的共同冷却及并发发送。

**beta.85 活跃用户：** 发布重启后恰好接收 2,000 条诊断，在 10:15:40.682 用尽日预算，Retry-After=49,460 秒直到 UTC 日界。重启前另有 339 条，解释了当天累计 2,339 条与 2,000/day 配置并不矛盾。此后检查该主体的全部凭证，直至统计窗口结束没有新增诊断，但有 **45 次模型调用**，观测缺口成立。

这 2,000 条中，metadata 合计 1,066,588 字节（约 1.02 MiB，**不含完整 HTTP/数据库开销**），P95 为 1,894 字节。同期限流前有 123 次模型调用；事件包括 257 条请求查询成功、223 条 transport_attempt 成功、223 条工具开始、213 条工具成功、123 条 provider request 开始、122 条请求形状等。不能把它们统称为异常重试风暴，也没有证据说明当时服务器存储或 CPU 已过载。

窗口另外 3 次诊断 429 位于旧容器时段，具体 limit_kind 缺证据，不推断。

### 3. 修复方向与验收

1. 保留 HTTP 请求/字节/并发防护，同时单独定义唯一事件的保存预算。不要把所有限制都移到去重之后，避免重复请求无限消耗解析和数据库资源。
2. 为可信的关键终态设计有界保留预算；事件类型及优先级须由服务端校验，不能允许客户端任意标为高优先级就绕过限制。普通成功轮询、重复阶段消息由客户端采样或聚合。
3. 批量接收应是版本化增量协议，旧 v1 保持可用；约束事件数、总字节、单事件大小，并返回逐项接收/重复/冲突/拒绝结果。不能以“一批算一次”无限放大事件预算。
4. 明确预算是否持久、采用什么重置边界，提供 remaining/reset/limit_kind 和服务端耗尽指标；当前限流告警有抑制窗口，不能用告警行数当作拒绝总数。
5. 先测量不同活跃程度、版本、事件类型的合理日量和峰值吞吐，再选限额；现有样本支持预算需要调整，不支持凭空选一个新数值。

验收覆盖旧客户端兼容、跨队列遵守 Retry-After、重复/冲突事件、部分批次失败、进程重启、日界切换、普通预算耗尽后的关键终态保留以及错误高优先级滥用。Gateway 负责协议、预算及观测；客户端负责排队、冷却、采样和稳定 event ID。

## 三、图片并发：共享池成立，但完整超时及工作生命周期更紧迫

### 1. 请求实际做了什么

| 路径 | 实际工作 | 现有限流 |
| --- | --- | --- |
| create | 本地生成上传签名，不访问 R2 | 普通 credential 桶，与模型共享 |
| 客户端 PUT | 客户端直接上传 R2 | 不经过 Gateway 入站限流 |
| complete | 首次 HEAD ready、HEAD 图片、GET 全图流式校验、PUT ready 标记 | 普通 credential 桶，与模型共享 |
| read-url | 检查资产并生成读取地址 | **已有独立 subject 桶**：20 并发、1,920/min、80,000/day |
| delete | 删除图片和 ready 标记 | 普通 credential 桶 |

complete 已 ready 的路径可通过元数据检查返回，不必每次下载全图。首次校验按流计算哈希，只保存少量文件头，不能说每次把最大 20 MiB 图片完整缓存在内存。[路由](../../apps/gateway/src/vision-asset-routes.ts)、[服务](../../apps/gateway/src/services/vision-asset-service.ts)、[read-url 策略](../../apps/gateway/src/services/vision-read-url-policy.ts)

09-26 已有三笔 complete 与一笔模型占满普通并发 4、随后 create 被 429 的历史证据，见 [责任边界调查](./client-timeout-upload-boundaries-2026-09-28.zh-CN.md)。本次固定 24 小时内 create/complete 各 13 次均成功，图片接口没有 429；不能把历史碰撞写成当天持续故障。

### 2. 新确认的生命周期缺口

**完整响应体不受所配超时保护。** 生产 R2 timeout 为 30,000 ms。`authenticatedRequest` 在 fetch 返回后清除计时器，实际 HTTPS transport 收到响应头就返回 Response；随后 GET body 的 `reader.read()` 循环没有完整操作或无进度期限。因此 30 秒既不是整个 complete 的总时限，也没有覆盖该下载流的全生命周期。

离线设为 1,000 ms，R2 返回响应头后暂停 body，1,500 ms 时 complete 仍未结束、信号未取消。主动继续流后才完成。线上尚未找到对应 body 停滞事故，不能以此解释所有用户图片超时。

**连接结束早于工作结束，名额计数失真。** complete/delete 未传递客户端 AbortSignal，也没有像 read-url 一样用 `withRateLimitWork` 保护工作生命周期。断开连接会释放普通并发名额，后台操作可能继续。离线用实际路由和限流/断连逻辑复现：断开前另一普通请求 429；断开后 complete 仍 pending，active 已为 0，新的普通请求变为 200。这是后台工作被漏计，不是名额永不释放。

**相同 pending 资产没有合并校验。** 两个并发 complete 会各自下载、校验并尝试写 ready；离线观察两次 GET 和两次 PUT。生产 ready 写入有条件请求处理，不能据模拟成功响应断言线上会生成两个标记或逻辑结果不幂等。这里的问题是重复工作。

### 3. 修复方向与验收

1. 先补完整操作期限、下载无进度期限、客户端取消传播与流关闭；并发租约持续到物理工作实际结束。即使依赖忽略取消，也不能提前放出名额。区分资产校验失败与取消/网络失败，避免把正常资产误删。
2. 再把图片上传控制与模型资源保护分开。complete 是下载与校验重操作，需 subject 和服务总量的有界保护；create 是轻量签名操作，delete 是清理操作，应按资源成本设计，避免重 complete 堵住清理。
3. 保留 read-url 已有隔离语义，不能照搬它的 20 并发给 complete，也不能误称所有图片接口目前都与模型共享。
4. 在生命周期正确后评估 owner+asset 的校验合并；必须有界清理、每次鉴权及独立 waiter 取消语义，不能因一个调用方取消就中断其他调用方。合并不等于取消入口防护。

验收覆盖仅返回头但 body 停滞、慢速持续传输、断连、忽略取消的依赖、同资产并发、校验失败清理、有效资产取消、多用户争用、图片与模型互不占用名额。再用不同图片大小和并发数压测，确定合理上限。
