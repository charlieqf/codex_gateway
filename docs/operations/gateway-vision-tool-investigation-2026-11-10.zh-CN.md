## Gateway 根因深入调查

### 同名工具修复缺少失败调用定位

三次腾讯 screenshot 失败的每次上游尝试都记录 `toolNames=["screenshot"]`、`toolCallCount=5`，即五个同名调用。事发版本与当前版本的 `nativeJsonRepairContext` 均只在同名匹配数等于 1 时向修复请求加入原始参数；超过一个匹配时明确告诉模型“rejected arguments are unavailable”。校验器虽然遍历时掌握失败调用的数组索引，但 `ToolCallValidationDiagnostic` 只保存工具名、字节数和语法位置，没有传递该索引。

本地合成五个同名 screenshot 调用，令第三个 JSON 语法错误，已复现：校验器找到语法错误，修复提示却不含这条错误参数。相同错误作为唯一同名调用时，原始参数及语法位置可以完整传入。此限制与三次生产 screenshot 失败的形状直接吻合，能解释为什么恢复步骤缺少关键输入；它不证明首次 JSON 语法错误由 Gateway 制造，也不能保证补全上下文后模型必然修复成功。

两次 bash 失败每次只有一个调用，不能套用上述解释：现有代码已给这一形状提供精确错误参数和位置。应保留单调用路径，并通过原始上游输出调查重复语法错误。webfetch 的首次失败是未调用工具，因此其修复请求当时也不可能预先知道随后会出现 timeout 参数类型错误。

可直接实施的修复是把已知失败调用索引保留为内部诊断事实，重试前按索引取出调用并再次验证工具名与字节数，避免猜测同名调用。参数仍只在当前一次有界上游修复中使用，不写入持久日志；保留 8 KB 上限、不增加尝试次数、不放宽 JSON/schema 校验。

### 标准流分片未复现参数损坏

使用当前真实 adapter 和 collector 重放五个并行同名工具调用，逐个工具按 3 字符拆分参数、倒序交错发送 index，并分别将 SSE 网络数据切成 1、7、31、4096 字节块。参数包含 Windows 反斜杠、引号和中文。四种网络分片下，五份收集结果都与原参数逐字节一致。

该验证排除了这些标准 indexed delta 形状下的拼接错误，不覆盖事发原始帧中可能存在的索引缺失、重复整串或非标准累积快照；原始帧未留存，不能声称已经逐笔排除了拼接因素。没有证据支持通过修改正常增量拼接来修复这些历史事件。

### 视觉下载错误被包装为通用 400

22:49 UTC 在生产容器内复用实际天宽视觉 adapter 做两个对照：64×64 合成 PNG 内联输入在 868 ms 内成功；一个不存在的 example.com 图片 URL 在 726 ms 后返回外层 HTTP 200、流内 `api_error`、`code="400"`。流内 message 明确写着下载图片得到 404，并带有天宽 Request id。Gateway 最终将它归为 `invalid_request`。这证明该供应商的“模型 400”可以表示供应商拉图失败，不能等同于客户端模型参数错误。

本地另有独立分类重放：若错误帧没有明确数字状态，同时含 `type=invalid_request_error` 和下载 `timed out` 消息，`inferredErrorStatus` 先匹配 invalid_request，归为 400；若同一帧明确给出 code 504，则正确归为 upstream_timeout。此为已复现的条件性分类缺陷，尚无证据证明历史 8 次走的是该条件。修复时应分别保存“数字状态是否明确”“供应商错误码”“拉图 HTTP 状态/超时类别”，避免用模糊关键词覆盖明确状态，更不能把下载 404 当作瞬时失败无限重试。

对照结果见 [供应商控制请求](../../.task-artifacts/gateway-vision-tool-20261110/provider-control-result.json)。这两个请求只使用合成数据；没有创建用户或写入生产数据库。

### 上游追踪 ID 丢失的具体路径

上述坏链接对照的上游错误消息带 `Request id: 021794264586713c2eb6daa98a94139fa98701b99e0cb3c260fb4`，Gateway summary 中 `upstreamRequestId` 仍为 null。检查实现确认：普通 HTTP 错误可从 header 或顶层 `request_id` 取 ID，但流内错误分支没有提取错误结构/消息中的 ID。独立合成重放也确认消息含追踪 ID、最终 summary 却没有。

历史 8 条 ID 为空不能再表述成“上游没有返回 ID”，只能说“Gateway 没有留存 ID”。旧容器日志丢失加上此提取缺口，导致无法直接用上游 ID 追踪原事件。优先补充流内结构化 ID 提取；供应商特定消息格式提取须严格限制字符和长度并防止凭据混入。随后将脱敏错误类别、来源、上游 ID 和 Gateway ID 持久化关联，不能依赖随容器删除的 stdout。

另外核对了 15 条失败的 model_calls 恢复回执：全部仍有失败响应，但视觉回执仅有通用 `MedCode upstream rejected the request.`，工具回执也不含原始参数。这些回执不能补回原始上游错误消息或工具帧。当前容器启动后至 22:48 UTC 的请求记录未出现新的这两类错误。

本地 [6 类重放结果](../../.task-artifacts/gateway-vision-tool-20261110/replay-result.json) 验证了以上拼接、同名修复、状态推断和 ID 提取行为；新增运行 adapter 与 native-tool-policy 两个现有测试文件，74 项全部通过。上述调查阶段只新增脚本、证据及报告，未修改业务实现。历史 8 次的具体原始错误与 5 次首次非法 JSON 的精确字符原因仍不能从已保留材料确定；已确认的 Gateway 恢复和诊断缺口可独立修复，不必等待上游完成历史追踪。

1. **同名工具调用修复定位。** 校验器在内部诊断中保留零起始 `toolCallIndex`。修复提示按该索引定位，并检查工具名和原始参数 UTF-8 字节数；索引缺失或无效、名称或长度不符时不猜测其他调用。上下文包含批次数量，并说明整批未执行、必须重新返回原任务需要的完整批次。保留 JSON 编码后 8 KB 限制、分隔符转义和一次修复预算，原始参数不进入持久诊断。
2. **流式错误追踪。** 上游请求 ID 优先使用有效响应头，其次提取错误帧顶层/嵌套结构化 ID，最后兼容 `Request id:` 消息格式。候选 ID 均经过现有字符、长度及凭据过滤；URL 内的内容不作为消息 ID 来源。普通 HTTP 错误也复用此提取路径。
3. **错误证据持久化。** 在现有 `upstream_attempts_json` 的每次尝试中增加 `providerError`，只记录来源、状态来源、分类状态、固定错误类别和可选拉图 HTTP 状态。外层 HTTP 200 与流内 400/504 分开保留，不保存错误原文、签名 URL、图片或工具参数；不需要数据库迁移。数据库关闭重开后仍能读取分类及上游 ID。
4. **有界状态推断。** 实际非成功 HTTP 状态、流内明确数字状态保持优先。没有数字状态时，明确图片下载超时不再被通用 `invalid_request_error` 标签遮蔽；可推断为 504，交给现有恢复策略。下载 404 等确定性失败推断为 400；明确的下载 408/429/500/502/503/504 可保留为推断状态。显式 400 即使消息提到超时或下载 503 也不改写。URL 中的 timeout 字样、timeout 参数校验错误不能触发此超时分支。

恢复仍遵守同一请求最多两次上游调用、已输出内容不重放、取消/截止时间立即停止、429 要求 Retry-After 等既有约束。没有放宽 JSON/schema 校验，也没有改正常 SSE 工具参数拼接。
