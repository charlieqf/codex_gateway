## 原因判断与诊断限制

四次明确超时的请求都带 `reasoning_effort=high`、`maximum_output_tokens=64000`，估算输入约 3.78–3.85 万 token。不存在这些请求被上下文限制或鉴权拒绝的事件证据。

同日成功请求也出现明显长尾：

- `req-be26995e-e74a-46aa-aa50-e1251a30353b` 耗时 575.136 秒，其中 reasoning tokens 为 24,222，首个适配器事件到 520.680 秒才出现。
- `req-fcfe86d0-788a-4e8c-8efd-1c31e1fc4ca1` 耗时 449.062 秒，输出 34,877 token、其中 reasoning 为 22,648，最终返回 1 个 `write` 工具调用，工具参数为 32,907 字节。（后续按数据库核对并校正了此处请求 ID。）

这些是“长推理或大段工具参数生成可能逼近总期限”的实证线索，但不能据此认定失败的四次请求也有同样的生成过程。

当前适配器实现有两个限制：

1. 推理内容不作为事件向下游发出；原生工具调用会先累积，再在流完成后发出。因此 `provider_first_event_ms` 是首个适配器事件的时间，不等于首个上游网络字节的时间。请求层 `first_byte_ms` 缺失时又回填结束时间。
2. 在响应流抛异常时，catch 分支未附带累积中的 `responseSummary`。因此失败记录中的上游 HTTP 状态、请求 ID、部分流统计会丢失；`contentChars=0` 和空 usage 不能证明上游完全没返回内容。`failure_stage=streaming` 本身说明流程已经进入有效响应体读取阶段。

此外，`UND_ERR_BODY_TIMEOUT` 尚未被传输错误分类表明确识别，因此两次响应体超时落到 `unknown`，进一步降低了当前监控的可解释性。

上述观察来自容器内与本地 SHA-256 一致的 `openai-compatible-provider.ts`、`chat-request-deadline.ts`、`observation.ts`。

## Gateway 侧继续调查：已验证结果

后续查询及代码复现完成于北京时间约 18:25。以下结论不依赖客户端团队补充材料，也没有修改生产服务。

### 1. 超时发生在工具完成后的模型调用

黄海东 30 页任务的顺序为：模型返回 `skill` 调用 → 客户端 `skill` 工具成功（225 毫秒）→ 模型返回 `medevidence` 调用 → 客户端 `medevidence` 工具成功（104.365 秒）→ 第 3 次主任务模型调用等待 600 秒后失败。

12 页任务的顺序为：模型返回 `medevidence` 和 `skill` 调用 → 两个客户端工具均成功（分别 114.031 秒、214 毫秒）→ 第 2 次主任务模型调用等待 600 秒后失败。

后续“继续”对应一次新的模型请求，直接等待 600 秒后失败。三次失败请求的客户端 `retry_index` 都是 0；Gateway 每个请求也只有一次上游尝试。用户新发“继续”与一次 HTTP 请求内部的自动重试不同。

这些记录可将故障点缩小到工具结果回传之后的腾讯模型调用。尚无证据确认该失败调用正在生成哪个工具，也不能说 PPT 本地写入工具已经执行并超时。前三个失败请求的工具循环评估均为 `allow`。

### 2. 推理和输出上限来源已核实

四次明确超时均记录：

- `requested_reasoning_effort=high`，`effective_reasoning_effort=high`，`reasoning_effort_source=request`；Gateway 没有在这些请求中把推理强度调高。
- `model_max_output_tokens=128000`，`maximum_output_tokens=64000`。

路由实现只在请求未提供输出上限时使用模型默认上限，当前池成员也没有单独的 64,000 上限覆盖。因此这四次请求的 64,000 来自调用方请求参数，而非 Gateway 的 128,000 默认值。这里的 64,000 是允许的最大输出量，不能当作失败请求实际已生成的 token 数。

### 3. 600 秒是总期限，不随上游活动刷新

从容器内应用配置解析得到：`goldencode/tencent` 请求总期限与腾讯适配器期限均为 600,000 毫秒。

`createChatRequestDeadline` 从单次请求执行开始设定计时器；推理片段、正文或工具参数到达不会重置它。因此上游持续生成也可能触发该总期限。这是当前期限策略的行为，不能将每次触发都解读为连续 10 分钟没有网络数据。

### 4. 本地复现证实异常退出会丢失流证据

使用与 R760 源码哈希一致的适配器和流统计代码，在本地注入人工 SSE 流，未发网络请求。复现脚本：`docs/outbox/r760-medcode-timeout-repro-2026-09-08.mjs`。

运行方式：

```powershell

```

三个场景的断言全部通过：

| 人工流场景 | 实际已送入适配器的数据 | 当前记录结果 |
| --- | --- | --- |
| 持续推理/工具参数片段，缩短为 350 毫秒总期限 | 11 帧、1,178 字节，错误前仍有片段到达 | 只有最终错误事件；`toolCallCount=0`、上游 HTTP 状态及 ID 为空、`rawResponseChars=67` |
| 同类工具参数流正常完成 | 5 帧、619 字节 | 到流结束才发出工具调用，成功保留 HTTP 200 和上游 ID |
| 收到片段后人工注入 `UND_ERR_BODY_TIMEOUT` | 4 帧、429 字节 | `upstream_unavailable / unknown`，上游 HTTP 状态及 ID 丢失，`rawResponseChars=71` |

这里 67 和 71 是 `ProviderStreamSummaryCollector` 回填的标准化错误事件长度，不是腾讯原始响应长度。已确认线上四次总期限超时的 `rawResponseChars=67` 同样不能用于推断实际收到了多少上游数据。

本地复现证明的是诊断数据丢失、工具缓冲及总期限行为，不代表成功重放了客户的真实失败输入。历史失败时已经丢失的推理/工具参数统计无法凭现有数据库恢复。

### 5. 约 25 秒的 HTTP 200 来自下游保活机制的可能性已定位

客户端在四次总期限超时开始约 25 秒时都记下了 `gateway_confirmed`；之后到约 600 秒记录终态错误。

`setupSseResponse` 每 25 秒向客户端写 `:ping`，即使没有模型输出也会发送。该写入能使先前尚未刷出的响应头被客户端接收。因此客户端约 25 秒时记下的 HTTP 200 与保活机制吻合，不能作为腾讯首字节时间，也不是一次已完成的成功推理。这里仍应区分代码机制与没有抓包的历史请求证据。

### 6. 另有独立的响应体空闲期限

运行环境为 Node `v24.19.0`、内置 Undici `7.29.0`。核对该运行时内置实现，默认响应体读取超时为 300,000 毫秒，收到响应体数据会刷新计时；当前适配器调用全局 `fetch`，未设置独立 dispatcher 覆盖这一默认行为。

所以总期限 600 秒与响应体读取空闲期限约 300 秒是两类限制。王云、郭泽麟的 `UND_ERR_BODY_TIMEOUT` 不能按请求总耗时 408/357 秒解释为空闲阈值就是 408/357 秒。现有记录仍不足以分清是供应商暂停输出还是中间网络不再转发数据。

该底层错误在分类表中缺项，已通过人工异常场景复现落入 `unknown`。应修正分类，但单独修正分类不会消除上游停顿。

### 7. 当前失败切换不覆盖这些流中超时

腾讯启用、天宽禁用的池配置已重新核实。当前原生工具失败切换只接受指定的上游 HTTP 错误或收到响应头前的网络错误；流中响应体超时不在允许范围内，总期限耗尽后也不能继续尝试。

因此这些请求没有第二次上游调用符合当前策略；仅启用备用供应商也不会自动解决同类流中超时。应先保留流进展证据，再评估重试或切换是否可能重复生成及增加用户等待时间。

截至北京时间约 18:25，本次继续查询的 17:57 之后已完成请求中未见新增 `upstream_timeout/upstream_unavailable`；这不等于故障已修复。

## 建议的后续工作

1. 优先补齐异常退出时的上游响应摘要，以及首/末网络活动时间、推理字符数和工具参数累计大小等元数据；不记录原始推理内容、正文或工具参数。为响应体读取超时建立明确分类。
2. 使用受控请求对比 `high` 推理及长工具输出的延迟，确认是否需要调整推理/输出预算或请求拆分。现阶段不应把单纯增加 600 秒上限视为已验证的修复。
3. 单独追查 xAI 的连接重置及同回合三次 HTTP 尝试，核对客户端重试契约与该路由策略。
4. 对客户端资源清理空 JSON 请求体和诊断上报限流分别建修复项。

本次完成只读调查、本地人工流复现及证据归档，未修改生产超时、模型路由、重试策略或用户账户。优先可实施的 Gateway 修复是异常流证据保留和响应体超时分类；客户端侧请求拆分或推理预算调整则需要受控对比，才能判断对真实任务的效果。
