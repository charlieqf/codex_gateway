# GoldenCode 单模型切流消费者与腾讯容量审计

审计时间：2026-08-04 17:41–17:42 AEST（07:41–07:42 UTC）

审计结论：**当前为 no-go，不能立即把公网模型面收窄为仅 `goldencode`。**
R760 四容器本身已经具备运行条件，但切流前仍须关闭以下硬门槛：

1. 最近 24 小时仍有 5 名有效用户调用 `max` 或 `pro`，最近 7 天有 9 名；
2. 腾讯共享账号的合同额度、RPM/TPM 和最大并发尚无账号侧证明；
3. 审计期间一条腾讯 provider credential 曾出现在操作终端输出中，必须按已暴露
   处理并在切流前轮换；该值未写入本文或 Git。
4. Azure 旧八模型 registry 中仍有 Qianfan、Aliyun 和 OpenRouter GLM-5.2 路由处于
   enabled；因此当前 Azure 整体尚未真正满足“所有 LLM 仅腾讯”的运行策略。

## 审计范围与方法

- 数据源是 Azure 当前公网 Gateway 与独立 Research LLM Gateway 的 SQLite
  `request_events`；查询以只读模式打开数据库并启用 `PRAGMA query_only=ON`。
- 30 天窗口为 `2026-07-05T07:41:10.953Z` 至
  `2026-08-04T07:41:10.953Z`。
- 远端 SQLite 查询没有创建文件、容器、凭据或数据库写入，也没有读取或输出完整
  用户 key、provider key、手机号或 secret 内容；另一次本地全文搜索造成的 provider
  credential 终端暴露已作为独立安全事件记录在上文。
- “观测 token”优先使用 provider 返回的 `total_tokens`，缺失时使用 Gateway
  `estimated_tokens`。它适合容量趋势分析，不等同于供应商结算账单。
- 并发峰值按请求事件的实际起止区间重建，只能证明历史上观察到的负载，不能证明
  腾讯合同允许的最大并发。

公网失败事件主要为 `client_aborted=19`、`tool_call_validation_failed=12`、
`upstream_unavailable=7`、`content_policy_violation=2` 和 `upstream_timeout=1`；
Research 有 1 次 `client_aborted`。窗口内没有记录到明确的 provider rate-limit
错误，但“未观察到限流”不能证明账号容量足够。

Azure 公网 Gateway 在 `2026-08-04T02:56:39Z` 重建并将 `goldencode` 收窄为
腾讯单路。至本次审计结束，该新路由窗口记录公网 194 次请求、192 次成功、
12,324,831 观测 token，并发峰值 2；同一时段 Research 没有请求。因此这段数据
证明腾讯单路能够处理当前公网样本，但没有同时覆盖公网与 Research 的叠加压力。

当前有效配置还有一个关键差异：

- 公网 `goldencode` 只有 `goldencode-tencent`，但该成员没有显式
  `maxConcurrent`；
- Research 只有腾讯成员 enabled，配置 `maxConcurrent=3`，Qianfan/Aliyun
  只是 disabled 条目；
- 两条路径可复用同一腾讯 credential，但 Gateway 的两个池、SQLite、服务 token
  和 Worker 路由仍然隔离。

所以不能把容量描述为“公网 3 + Research 3 = 6”。公网当前没有本地显式上限，
历史共享账号的重叠峰值只观察到 3，而腾讯账号侧允许的总并发、RPM、TPM、日额度、
余额和到期边界均未从供应商控制台或合同得到证明。

## 切流前关闭条件

1. 把上述 9 名近期消费者及所有仍有效的旧模型客户端改为
   `model=goldencode`；至少连续 24 小时复查 `max/pro/...` 请求为零。
2. 在受控变更窗口移除或禁用 Azure 旧 registry 中仍 enabled 的 Qianfan、Aliyun、
   OpenRouter 和 Codex/其他文本模型路由，并验证 `/v1/models` 与拒绝行为符合最终
   单模型契约；不得把近期零调用误当作已禁用。
3. 从腾讯控制台、合同或供应商支持取得共享账号的最大并发、RPM、TPM、日/月额度、
   余额和有效期证据，并据此为公网池设置明确的 `maxConcurrent`。
4. 在不影响真实用户的受控窗口，从 R760 同时施加公网与 Research 负载，验证排队、
   超时、取消、错误率和 token 峰值；不能只分别做单路 smoke。
5. 轮换审计期间暴露的腾讯 provider credential，核对引用它的 Azure、R760 公网和
   R760 Research secret 文件，并分别做 Tencent-only smoke。轮换过程不得打印 env、
   secret 或渲染后的 Compose 配置。
6. 继续关闭迁移方案中的其他独立门槛：CN1 `gw` vhost/证书与端到端验证、最终一致
   同步/写入冻结、Gemini 受支持地区出口、备份和回切演练。

本审计仅执行了只读检查，没有授权或实施模型删除、客户端修改、provider credential
轮换、CN1 Nginx/DNS 变更或公网切流。
