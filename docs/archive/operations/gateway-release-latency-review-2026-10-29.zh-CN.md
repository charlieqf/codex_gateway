## 优化优先级

1. **发布前把候选物与验收脚本准备完成。** 代码冻结后自动执行干净归档构建、测试、配置差异校验、数据库副本演练和模拟验收，把 revision、镜像摘要、配置哈希、原容器 ID 与测试结果绑定。发出正式切换指令时只重新校验来源及现场状态、取得必要的新备份、等待空闲、切换和验收。提交、配置、原容器或备份要求发生变化时，精确使相关证明失效，不能直接复用过期结果。
2. **把配置变更纳入通用发布事务。** 本次需要现场改造仅允许模型注册表变更的旧脚本，浪费了时间。后续统一使用严格的环境变量白名单、JSON 子项合并、保护文件校验、原子替换与回滚；本例只允许两个模型预算和三个 adapter。将准备、发布、验证写成同一可恢复命令，记录逐阶段起止、耗时和失败原因，避免重复 SSH 与人工接力。不接受任意环境文件整份覆盖。
3. **修复依赖安装缓存布局。** `deploy/r760-clinical.Dockerfile` 现在先 `COPY . /app` 再 `npm ci`，任何源码变化都会使依赖安装层失效。按普通 Dockerfile 的模式，先复制所有 workspace manifest、锁文件及 postinstall 脚本安装依赖，再复制源码。锁文件或安装脚本变化必须重装；继续在干净候选上构建和跑全量测试。实施前后需以相同源码改动做冷/热缓存对照，当前尚无节省秒数的实测结论。
4. **发布准备中的独立步骤并行。** 归档来源验证完成后，镜像构建可与备份、候选配置生成并行；备份完成后副本校验可与剩余构建并行。只有全部前置检查成功才允许进入排空。Git 操作、生产配置写入和切换仍串行，不同时跑多个大备份造成 I/O 争用。
5. **验收按公开契约断言。** 正常有界工具格式修复不应被“只能一次尝试”的断言误报。保留最终工具数、参数、终态、总预算、档位和跨尝试结算断言，对实际失败只重测受影响的检查。本次没有重跑已通过的六项 GLM。后续将模型专属允许行为做成测试数据，并在切换前用模拟收据覆盖“正常格式修复”样本。不要把失败计为成功或删除初次失败证据。
6. **区分上线确认与详细报告。** 两个模型的请求头、真实期限、健康与必要清理通过后，立即给客户端明确的“已上线”结论；详细报告整理和无关历史查询不应继续阻塞客户端发布。系统与数据完整性检查依然是发布验收的一部分。

## 本轮已消除的确定性阻碍

`gateway-drain.py` 在导入本地 helper 前设置 `sys.dont_write_bytecode = True`。即使历史调用方不传 `python -B`，也不会在不可变发布目录里留下 `__pycache__`，避免下次 prepare 因目录多出生成文件而中止。新增真实子进程回归：不带 `-B`、忽略环境变量，执行复制出的脚本 `--help`，验证目录文件及字节完全不变。原有空闲、排空和失败恢复测试保留，21 项 Python 测试通过。

这项脚本修正只影响以后发布，不修改线上运行源码，不再次重启服务。没有削弱 prepare 的未知文件检查。
